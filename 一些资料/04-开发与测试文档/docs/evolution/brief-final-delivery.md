构建交付工程师任务说明

本任务负责 E5-06、E5-04 的实际部署停止与恢复专项，以及前五阶段公开交付资料的汇合。根目录原有修改、Wiki资料和发布脚本选择规则已经单独保存，继续按照当前允许的公开目录生成交付包。`docs` 和 `.local` 保存内部推进及验证资料，公开使用说明在 Wiki 中整理；公开文件应省略私人称呼、个人绝对路径、临时凭据和本地验证数据库信息。

先读取 `scripts/build-release.py`、`scripts/verify-release.py`、发布测试、工具链和镜像锁，以及 `handoff-edge-stop.md`。第一阶段已完成 CE/Edge 原生通信与 Envoy 实际验证，Edge 的 PID1 shell 向 Java 传递停止信号仍待确认；需要在正式部署准备和停止入口中处理，并用保留数据的临时服务完成实际停止及再次启动。运行证据要记录应用关闭、数据库事务结束、实际退出码、耗时和容器OOM状态。

最终交付包含当前两个Go模块、三个前端入口、生成契约、编号迁移、部署与兼容清单、依赖来源及许可、公开说明和运行脚本。构建目标遵循现有 Linux amd64 交付要求，隔离程序发布验证需要的本机目标由发布协调工程师提供或协商构建。最终发布清单保存实际文件与组件摘要，源码与构建输出可相互核对。

公开说明应覆盖新的草稿流程、连续模拟、任务详情、控制核对、回放比较与影子计算、告警工单和交接、模板、AI依据、节点配置和分批发布，说明各项角色、条件、实际操作与错误处理。数据库、Kafka、NATS等迁移步骤引用已经验证的过程，保留支持的恢复与退回条件；历史版本页面继续记录对应历史版本，当前版本页面与实际产物一致。

验证流程如下：

1. 修复并验证正式 Edge 停止入口，保留原始和派生数据后再次启动，核对消息重复处理、平台审计及资源释放
2. 核对依赖、镜像、工具链、兼容清单、契约和迁移编号，执行两个Go模块、前端、契约及适用有限协议与云边回归，记录环境跳过与补充验证
3. 从最终源码构建交付包，执行 `verify-release.py`、包内文档链接、公开文件与许可检查，按摘要验证二进制和前端输出
4. 使用包内入口完成一次隔离安装准备及服务运行检查，核对包内运行版本、规则与配置，验证退出和再次启动过程
5. 形成 `.local/evolution/final-delivery-verified.json`，列出可交付目录、文件数量和大小、构建环境、命令与结果、测试规模、受测源摘要及仍需独立审查的事项

完整UOS安装恢复、连续断云24小时、受限链路专项与实际24小时容量测量沿用本轮范围约定。必要依赖及镜像获取已获授权，先安排Docker和工作卷资源；产物可保存在工作区允许目录或 `/private/tmp`，最终提供可访问路径。主协调者与独立验收工程师按45项清单核对后确定整体完成状态。

消息基础设施专家按官方相邻升级指南验证NATS2.11.9经锁定的2.12中间版逐节点进入2.14.7，精确tag和摘要以 `message-infrastructure-verified.json` 为准。最终离线迁移材料需要提供该中间镜像或可复现的锁定准备流程，并核对最终包的依赖清单和实际包含内容一致。Kafka需分别说明保留旧metadata时的二进制退回，以及metadata推进后的备份恢复步骤，附受测持久目录与消息/消费位置的核对依据。

实施前同时读取 [消息交付交接](handoff-message-delivery.md)。第二阶段完成NATS旧版三节点冷备、旧版冷重启、目标升级和目标重启；最终恢复验证还需使用保存的旧版冷备建立独立三节点项目，保留服务器身份与签名材料，核对检查点、执行权和消息一致性，并登记备份之后的数据补回范围。Kafka在元数据推进之后已有独立冷备恢复的实际证据；在Docker Desktop下恢复目录采用独立路径，并从容器内部核对文件摘要。正式组合资源配置与迁移夹具预算分别记录，按最终包配置执行适用运行检查。

前端工具链使用npm包别名，最终组件清单需要同时保留安装位置与实际发行包身份。当前`build-release.py`从node_modules路径生成module/id，会将`@typescript/native`记为发行包名；锁文件明确给出其name为`typescript`、version为7.0.2，`typescript`位置实际为`@typescript/typescript6`6.0.2，内层`@typescript/old`实际为`typescript`6.0.2。按锁文件的name、version、resolved与integrity记录实际来源，并将别名和安装路径另外保留；核对许可证和组件标识，避免不同别名及版本的许可目录互相覆盖。此项属于最终发布清单实现，使用现有锁文件和真实构建产物验证。

第二阶段独立回归保留六项DataTransfer条件跳过，见 `phase2-independent-review.json` 的 `conditional_skips`。最终适用协议回归需准备OPC UA外部服务及签名加密证书夹具、HTTP扩展进程、MQTT代理，并实际执行 `TestNativeClientExternalSmoke`、`TestNativeSignedEncryptedMethodAndCertificateValidation`、`TestHTTPExampleProcessCollectsAndControlsSimulator`、`TestExternalBrokerSmoke`；A06的 `TestDurableMessagesFaultInjection` 按现有100000条有限样本运行，并核对其 `TestDurableProcessFixture` 子进程实际启动。普通顶层测试中用于子进程的夹具自身跳过时，按实际父测试证据说明。该项与本轮排除的连续24小时专项分别记录。

第五阶段程序发布集成依据 `docs/evolution/release-deployment-contract.md` 与节点身份契约执行。最终包中的 `sf-release-agent` 应当管理实际程序进程，并保留节点原有数据库、主密钥、云边同步、NATS及原生平台和网关选项；验证使用正式准备入口生成的身份、TLS配置和持久目录。节点配置专家完成准备脚本交接后再安排这些文件的修改，公开记录保留凭据引用和临时夹具说明。

首次将原 Edge 改由发布代理管理时，原 Edge 同时可能是连接器密钥的所属服务；使用发布专家提供的 `--prepare-only` 在原服务仍在线时完成当前身份、发布目标及工件核验并加密暂存，再正常停止旧服务并使用原数据库和主密钥启动代理。实际部署检查覆盖首次转换、源服务退出后的缓存启动，以及准备后目标改变时当前分配与缓存的核对，最终参数以更新后的发布部署契约为准。
