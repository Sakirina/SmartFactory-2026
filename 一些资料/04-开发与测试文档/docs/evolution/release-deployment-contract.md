发布代理与正式部署契约

`sf-release-agent` 管理受固定发布约束的实际 `sf-edge` 子进程，程序工件必须能通过 `-build-info` 返回程序版本、操作系统、架构、数据库范围及构建来源摘要。云端将程序、规则和配置组成不可变发布，代理按工作负载当前分配取得内容，校验工件后正常停止旧进程，等待进程退出，再启动新进程；每次切换的旧 PID、退出时间、新 PID 和就绪时间保存在私有代理目录的 `last-transition.json`。

正式部署将代理目录与业务状态目录分别指定。`--dir` 保存工件缓存、加密发布载荷、当前状态和切换记录，`--runtime-config` 指向权限为 `0600` 的 JSON 文件，其中 `database` 使用原有 PostgreSQL DSN 或 SQLite 绝对路径，`master_key_file` 使用原有主密钥绝对路径，`static_directory` 使用包内前端目录。`environment` 保存原 `sf-edge` 的 `SF_` 与 `OTEL_` 环境配置；程序继承云边同步、NATS、ThingsBoard、原生平台转发、DataTransfer、各服务证书和观测配置。

`SF_NODE_ID`、`SF_LISTEN`、`SF_DATABASE`、`SF_MASTER_KEY_FILE` 和 `SF_RELEASE_PAYLOAD` 由代理提供，运行设置文件使用相应字段和启动参数声明前四项。原有 `SF_SERVICE_TOKEN` 可以放入私有 `environment`，代理沿用它验证本地运行信息；未提供时，代理首次启动生成仅拥有者可读的令牌。初始管理密码可通过 `--bootstrap-password-file` 提供，已有用户和权限继续从原数据库读取。生产启动使用原实例数据；`--seed` 仅用于本轮隔离验证夹具。

| 参数 | 作用 |
| --- | --- |
| `--cloud` | 云端发布与身份权威服务的 HTTPS 根地址，使用专用 mTLS 监听 |
| `--config` | 独立配置中心 HTTPS 根地址 |
| `--node-id` | 已登记节点身份，与工作负载绑定一致 |
| `--token-file` | 私有工作负载令牌文件，发布代理与普通配置订阅程序使用不同用途和实例 |
| `--listen` | 被管理 `sf-edge` 的原有服务地址 |
| `--runtime-config` | 原数据库、主密钥、前端目录与服务环境配置 |
| `--dir` | 私有代理状态与发布缓存目录 |
| `--ca`、`--cert`、`--key` | 代理访问云端和配置中心时使用的 CA 与节点客户端证书 |
| `--bootstrap-password-file` | 新安装的初始本地管理员密码文件 |
| `--poll` | 期望发布查询周期，默认一秒 |
| `--prepare-only` | 首次服务转换时，在原 Edge 在线期间核验当前分配并加密暂存发布；完成后退出 |

启动形式如下，部署工具应替换占位路径，并将原服务环境整理进私有运行配置文件。

```sh
sf-release-agent \
  --cloud https://cloud:18445 \
  --config https://config:8092 \
  --node-id edge-a \
  --token-file /state/identities/release-edge-a.token \
  --listen 0.0.0.0:8091 \
  --runtime-config /state/release-runtime.json \
  --dir /state/release-agent \
  --ca /state/pki/ca.pem \
  --cert /state/pki/edge-a.pem \
  --key /state/pki/edge-a.key
```

首次从原 `sf-edge` 服务切换到代理管理时，部署工具按以下次序处理。

1. 保持原 Edge 及其连接器密钥解析服务在线，使用上述代理参数附加 `--prepare-only`，等待当前身份、发布分配、程序工件和固定配置核验完成，取得准备回执与加密暂存记录
2. 正常停止原服务，保留业务数据库、主密钥、证书和采集器状态，然后去掉 `--prepare-only`，使用原服务地址和同一私有代理目录启动代理
3. 代理取得新的认证实例后再次查询当前分配，并核验配置目标；准备期间目标若已改变，代理按当前发布重新准备，最近的待完成文件继续接受当前分配核对

后续发布由代理完成进程切换，系统服务管理器持续管理代理。代理退出会正常停止它已验证归属的子进程；代理异常退出后，新代理核对缓存与实际进程摘要、节点、PID 和进程实例，能够继续管理仍在运行的子进程。

发布缓存中的配置载荷使用节点既有主密钥，通过现有 `identity.Manager` 的 AES-GCM 加密保存，认证附加数据包含节点及发布摘要。`active.json` 保存最近已运行内容，`pending.json` 保存正在切换的声明和新进程 PID；代理异常退出发生在新程序启动与当前状态更新之间时，新代理通过待完成记录核对实际进程后补全当前状态。配置中心和云端不可达时，代理可以先从加密缓存启动最近已确认的程序，再恢复在线身份和当前分配核验。

缓存程序通过身份、内容和工件摘要检查后，若实际子进程退出或等待就绪超时，代理在 `restore-status.json` 保存发布任务、代际、摘要及启动失败原因，并继续查询云端分配。同一任务、同一代际和同一发布保持失败状态；人工重试产生新代际或云端分配新任务后，代理再次准备并启动程序。代理重新启动会读取这份失败记录，核验原缓存和工件后继续等待授权；缓存认证失败、工件摘要变化或已有进程无法认证时，启动检查直接返回对应错误。

程序转换导致所属 Edge 密钥源暂时离线时，代理完成当前发布分配与固定版本读取后，可以从当前发布、已运行发布或待完成发布的加密缓存中取得完全相同的固定配置密钥。代理逐项核对配置引用、节点、程序、用途、配置正文、密钥引用及凭据代次，随后向在线云端重新核验当前身份、授权范围、`credential.resolve` 能力和认证实例。缓存仍使用原节点与原发布摘要完成认证解密，新载荷按新发布摘要重新加密；密钥解析返回 `401`、`403` 或 `409` 时，代理保留该授权或内容错误，等待身份、分配或固定版本问题得到处理。

使用 `SF_RELEASE_PAYLOAD` 启动的业务程序，从核验通过的固定载荷初始化配置；先前发布已移除的本地参数保持缺失，载荷包含的参数按固定版本恢复。配置权威保存的 `parameter_version` 使用固定配置版本，本地 `documents.version` 与 `document_versions` 使用连续的修改版本；重新应用旧固定配置时，本地修改版本继续递增，配置权威的既有固定版本保持原内容。

普通进程运行配置中的 `SF_CONFIG_AUTHORITY_URL` 与 `SF_AUTHORITY_LISTEN` 等设置应保留，使所属 Edge 的连接器密钥解析服务继续可用。连接器公开固定版本由云端同步记录及受验证的所属节点登记取得，配置中心保存公开固定版本，密钥通过原工作负载身份从所属 Edge 解析；代理继续调用配置中心的固定版本与密钥解析接口。运行快照会核对 DataTransfer 实际消费者内容及应用代次，固定发布与普通保存之间的应用规则由 `configuration_local_release_target` 控制。

受支持的旧发布退回继续使用当前数据库和历史记录，旧程序必须能读取当前迁移版本。只有数据库当前发布摘要与目标发布一致时，程序才复用既有规则激活记录；返回其他固定发布时，程序重新发布其规则并创建新的本地应用版本，同时禁用目标发布未包含的规则。固定规则来源版本和新建本地应用版本分别保存；连接器固定来源版本和 DataTransfer 应用代次也分别保留。数据库超出旧程序范围时，发布接口拒绝该退回，并返回恢复条件。

超出直接退回条件时，执行以下恢复流程，具体备份及还原选项沿用[运维说明](../implementation/operations.md)。

1. 正常停止代理及对应数据写入程序，保留当前业务状态目录，并确认待恢复备份对应的程序、迁移清单和主密钥
2. 执行 `python3 scripts/backup-state.py verify <备份目录>`，核对清单、文件摘要和数据库检查结果
3. 执行 `python3 scripts/backup-state.py restore <备份目录> --output <新的恢复目录>`，PostgreSQL 使用该工具的 `restore-postgres` 子命令写入空数据库
4. 使用恢复的数据库与原配套密钥设置新的私有运行配置文件，补回备份之后需要保留的数据，再以备份支持的程序启动并核对运行、规则、配置与审计记录

`scripts/verify-release-coordination.py --directory <新的私有验证目录>` 构建固定源码副本，运行独立云端、配置中心、两个实际节点及各节点的 DataTransfer 配置消费者；采集器夹具使用正式 ConfigManager、连接器 Manager、持久化日志和 gRPC，协议适配器在隔离进程内读取已应用配置。结果目录保存编译输入与外部依赖副本、逐次构建前后摘要、二进制摘要、HTTP、批次状态、规则实际输出、原始失败和进程退出记录。`--keep-running` 在全部验证通过后保留服务，并生成供前端使用的 `frontend-fixture.json`；其中凭据只提供私有文件路径。发布协调最终验收以 `.local/evolution/release-coordination-verified.json` 关联的成功运行和补充条件为准。
