控制执行工程师任务说明

本任务在第二阶段存储与计算接口验收后启动，负责 E3-01 至 E3-03，以及 E3-07 的控制执行时间线。主协调者负责验收和跨角色协调，历史计算工程师负责回放、版本比较及影子计算，前端工程师负责相应页面。任务开始前读取当前 [验收清单](acceptance.json) 和第二阶段最终接口说明，当前说明中的源码位置只用于定位基线，实施时再次核对文件状态。

现有 `internal/control` 已包含 Create、Approve、Dispatch、Run、动作日志、执行权核对及启动后的重复请求处理。`action_journal` 在设备发送前保存 `reserved` 记录，重复请求根据 command_id 与 payload_hash 判断；未取得明确结果的执行进入 `result_unknown`。既有测试覆盖会签、审批过期、撤权、组织变化、物理互锁、逐步骤再次检查以及服务恢复后的动作去重。这些行为需要纳入集中状态转换与持久记录，并继续通过回归。

实现应集中定义审批、资格检查、排队、执行、降级、结果待核对、完成、失败和取消等实际需要的状态与事件，明确每次转换所允许的来源、角色、对象版本及审计内容。当前分散的状态写入需要逐条映射到新的转换入口，普通请求、自动策略、定时策略、远程步骤、云边回执和恢复流程都使用相同转换规则。数据库保存、同步记录、审计及后续任务继续遵守第二阶段的原子提交和日志顺序约定。

授权检查覆盖执行所引用的规则、条件资源、正常与降级步骤设备以及所属组织；人工审批和恢复检查当前身份、授权及引用版本，自动策略依据已发布策略与对应服务身份执行。验证包括审批期间资源迁移、授权成员变化和身份停用，并通过直接应用调用与 HTTP 调用检查一致的处理结果。

结果待核对的执行应查询对应命令和设备反馈，将反馈来源、采集时间、命令身份及内容摘要保存到执行记录。人工操作按当前状态提供取消、核对和恢复，保留操作者、理由、expected_version 与支持其判断的证据；设备结果仍无法确定时保持待核对。已经完成的步骤、相同 command_id 及参数不符的重复请求需要继续具有确定处理结果，恢复前再次检查当前授权、规则版本、条件、执行权和物理互锁。

验证流程如下：

1. 为集中转换表运行合法与非法事件检查，覆盖批准后撤权、审批或启动过期、规则和参数变化、组织成员调整、不同角色及同时操作造成的版本冲突
2. 在动作预留前、预留后发送前、发送后确认前、保存结果前及进程恢复时分别注入故障，核对实际发送次数、持久日志、执行状态和审计；覆盖重复 command_id、相同身份内容变化与执行权失效
3. 使用明确设备反馈完成核对及合法恢复，验证无反馈、过期反馈、错误命令反馈和不同资源权限的拒绝；取消与恢复操作必须有实际 API 和持久状态证据
4. 运行现有控制、远程步骤、协调竞争和短时三节点实际 NATS 回归，使用消息基础设施工程师已经验证的目标镜像及持久格式，记录版本与有限测试规模，保留原有长期离线专项的范围约定；同时核对第二阶段每进程控制并发许可的取消和释放行为
5. 提供执行详情、允许操作和时间线 API，关联审批、每次状态变化、动作、回执和运行追踪；将字段、状态、错误及示例写入 `control-frontend-contract.md`，由前端工程师完成浏览器流程

文件归属包括 `Platform/internal/control`、控制相关应用用例、API、模型、协调与设备结果查询的必要适配，以及测试和控制说明。任务详情、通用 River 调度与历史计算语义由对应负责人维护，涉及共享 `app.go`、API 注册、模型、迁移、兼容清单和契约生成时先协调。新增迁移沿用已经确定的下一编号，已应用迁移文件保持校验值。

控制用例与动作核对沿用第一阶段OpenTelemetry基础，追踪关联执行、命令、对象版本及请求身份，计量状态判断、等待和发送结果时使用固定操作与有限结果维度。故障验证同时核对相应追踪与业务记录，参数及凭据明文省略。

最终报告为 `.local/evolution/control-execution-verified.json`，逐项对应 E3-01、E3-02、E3-03 和 E3-07 的控制部分，包含实际命令、退出状态、输入条件、动作次数、数据库与审计结果、受测文件和二进制摘要。开发与验证使用本轮隔离的模拟设备及临时实例。

已有控制记录需要能够继续执行合法的核对和恢复：使用迁移前执行状态、审批记录与动作日志建立实际样本，验证启动后的读取、允许操作、去重和版本冲突。过去没有保存的转换时间与反馈保持其实际缺失状态；新增时间线可以引用已有审计和动作记录，并明确每条信息的来源。若新增持久字段或表，沿用当前下一编号迁移，保留已经应用的文件校验值。

当前 DataTransfer 桥的 `Send` 通过 `SendCommand` 取得带 command_id 的响应，命令服务在自己的持久日志保存请求摘要和执行结果；现有协议尚未提供只读的命令结果查询入口。结果核对需要通过实际适配器读取已有记录，查询命令不存在时返回明确状态，查询过程保持设备动作次数不变。必要的只读结果查询协议、DataTransfer命令日志读取和平台桥适配属于本角色的控制职责范围，现有协议字段编号与命令发送行为继续通过兼容回归。反馈保存其实际来源和时间；通用设备当前值与绑定命令的执行回执分别按其含义处理。

第二阶段已交付实际使用的领域存储接口，见 `application/repositories.go` 与 `tasks/repository.go`。本阶段新增和改造的应用路径也应持有所需的存储接口，把驱动选择和SQL操作保留在存储实现；接口需用于生产调用。共享修改采用明确归属：新增模型优先放在本角色独立文件；现有Execution结构及控制注册由控制专家维护，独立分析模型及历史任务注册由历史专家维护。API总注册、app.go、Go模块、迁移注册和契约导出器的编辑时段由主协调者分配，新增持久迁移先申请当前下一编号并保留旧文件校验值。

当前生产入口复核还发现两处需要共同处理：`app/workers.go` 的 edge_downlink、strategy_trigger、scheduled_execution，以及 `coordination/commands.go` 的 Resume 都调用Control.Run；`cloudsync/exchange.go` 的cloud_receipt分支直接在事务中写入Execution及receipt_cursor。云端回执采用来源版本去重，本地文档版本独立递增，集中状态转换和时间线需要保留该语义，并覆盖乱序及重复回执。`coordination/coordinator.go` 当前将result_unknown视为终止状态，从Active移除且同一fence禁止改写终止Journal；人工核对与合法恢复应明确取得当前执行权并验证这段规则，继续防止自动流程在结果未知时再次发送设备命令。相关云边回执与协调适配属于控制专家本阶段范围。

消息基础设施已提供 [控制专家交接](handoff-message-control.md)：目标NATS2.14.7实际三副本验证通过，旧格式签名检查点已从2.11.9经2.12.15迁移；执行权来自KV修订，按大小关系判断，不能假设每次递增1。后续改动应使用交接中的旧检查点样本验证兼容读取，新增状态与恢复语义通过当前目标版本复测。

取消请求应注明对当前与后续步骤的实际作用：已经发送但结果未知的动作继续保留原命令记录、核对入口和后续反馈处理，尚未执行的步骤按取消状态停止推进。人工操作后的时间线保存取消请求与动作反馈各自的时间和来源，UI允许操作与这些状态一致；后续较晚反馈按原命令归属更新相应记录，并保持已确认结果的顺序。

人工干预支持云端与现场两种入口。云端已有创建、审批和下发路径，取消、核对和恢复继续通过持久的`edge_control_operation`交由拥有设备日志与当前执行权的边缘处理，再经`cloud_receipt`返回结果与时间线。云端受理返回操作身份和等待状态，边缘重新检查当前权限、引用版本、执行权及请求有效期；云端文档版本与边缘来源版本独立核对。使用两个实际应用验证重复操作身份、内容变化、离线等待、过期、处理时撤权及乱序重复回执，时间线分别保存请求发起、边缘处理和反馈的时间及来源。
