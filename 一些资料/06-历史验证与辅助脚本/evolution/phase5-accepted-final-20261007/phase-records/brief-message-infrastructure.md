消息基础设施迁移任务说明

本任务由已有工具链与原生集成工程师继续承担，完成 Kafka 4.3.1 与 NATS 2.14 系列的持久数据兼容验证及正式部署选版。当前两个目标镜像已经取得，Kafka 4.3.1 已参与 CE/Edge 原生通信验证；正式 dependencies、images.lock、生成部署与 toolchains 中仍保存旧版，需要在迁移验证通过后统一更新。任务按第二至第五阶段的消息基础设施目标执行，主协调者在同时运行名额空缺时安排启动。

实施前读取第一阶段最终报告、`deploy/dependencies.json`、`deploy/toolchains.json`、`deploy/images.lock.json`、部署生成脚本及当前协调测试。旧版 Kafka 4.0.0 与 NATS 2.11.9 的缓存镜像可以用于创建隔离的迁移源实例，所有数据目录、端口、网络及证书使用本任务独立名称。现有持久实例及此前保留的 PostgreSQL 验证数据库继续保持原用途。

Kafka 验证需要包含已有主题、分区、消息及消费位置，从旧版持久目录按官方支持的升级路径进入目标版，核对消息内容、偏移、消费与新消息写入。明确元数据版本更新的时机及其对退回的影响，并记录实际执行步骤；若官方路径要求经过中间版本，记录其原因并完成相应步骤。原生消费兼容已有第一阶段记录，本次仍需用实际队列证明迁移后的旧消息与新消息可读取。

数据库工程师检查部署时发现，`prepare-deploy.py` 生成的Kafka健康检查使用bash TCP探针，提交的`compose.native.json`使用`kafka-broker-api-versions.sh`。本任务核对这两条入口的就绪条件并统一适用配置，用目标版实际启动验证；数据库工程师只更新了PostgreSQL相关服务与卷配置。

NATS 验证需要包含实际三节点、双向 TLS、JetStream 持久 KV、执行权序号及检查点。利用现有协调用例验证目标版上的竞争、失效执行权、节点恢复与检查点读取，并用旧版写入的数据完成受支持的升级和重启流程。控制状态机的业务变化由第三阶段控制工程师承担，基础设施工程师负责发现并定位组件或部署适配问题。

验证流程如下：

1. 查阅正式发行与升级文档，核对目标摘要、旧数据目录和元数据兼容条件，保存来源和实际受测版本
2. 建立旧版隔离实例，写入可核对的数据和消费状态，完成目标版迁移与重新启动，检查旧数据、新写入及消费连续性
3. 对 NATS 执行短时三节点实际协调与 mTLS 检查，保存成员、复制状态、执行权和检查点证据；对 Kafka 保存主题、消息和消费位置的前后结果
4. 更新正式依赖、摘要锁、生成配置及相关文档，运行一致性和部署生成检查，核对运行镜像与声明镜像相同
5. 结束本任务临时服务，保留必要的迁移证据，形成 `.local/evolution/message-infrastructure-verified.json`，说明已验证的恢复与退回方式，并向第三、第五阶段交接

共享部署文件修改前与当前数据库或前端工程师协调；Go 模块修改交给当时唯一写入者。必要依赖和镜像获取已获授权。Docker 可用总内存约7.75GiB，应按实际运行服务逐项预留容器与 JVM 预算，避免与 PostgreSQL 专项竞争连接或内存；工作卷至少保留1GiB。
