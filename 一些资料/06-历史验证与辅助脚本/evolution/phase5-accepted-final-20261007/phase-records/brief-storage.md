存储与后台任务工程师任务说明

本任务覆盖 E2-01 至 E2-05，以及 E2-09 的后台任务详情部分。负责人完成存储、归档和调度实现，主协调者负责需求核对、跨角色协调与验收。当前规则工程师负责编译计划、确定性计算和连续模拟；AI 协议与前端分别由其他专家角色负责。每次新建或恢复工作均遵守全团队同时最多两个子智能体的限制，工程师不再自行创建子智能体。

开始前读取 [存储交接](handoff-storage.md)、[事务顺序](storage-lock-order.md)、[逐项验收](acceptance.json) 和 [实施计划](plan.md)。现有检查点已调整部分事务机制并取得 River 依赖，实际并发、归档计算外移及 River 业务替换仍待完成。既有 Goose 迁移 1 至 3 的文件字节和校验值已经进入第一阶段证据，后续新增迁移从 4 开始。

事务改造需要通过 PostgreSQL 实例验证：不同对象可以同时进入业务回调，同一对象及尚不存在的对象具有可解释的竞争结果；授权集合变化、同步日志、每源审计哈希链、inbox、outbox 与任务记录继续遵循业务事务。日志序号必须在最终提交锁内分配，测试应安排较早开始的事务延迟提交，同时完成另一笔事务，并实际读取增量游标，检查是否遗漏数据。数据库死锁与可重试冲突需要保留可识别的错误和 HTTP 409，禁止在 Store 内自动重复业务回调。领域调用通过明确的查询、写入和任务接口使用存储，审查遗留绕过接口的数据库写入及分区创建、退休竞争。

并发证据除 Store 的独立对象测试外，还需包含实际应用调用的独立业务样本。当前检查点的集合锁和 Tx.Get 采用保守的排他语义，多个用例可能共同读取同一个用户、授权集合或依赖；请测量这些共享读取对实际并发的影响，说明需要串行的条件与能够并行的流程，在保证授权及成员变化检查正确的前提下调整过大的锁范围。

归档候选读取、编码、压缩与完整解码校验应在最终业务写入事务之外完成。提交时按原始记录身份及内容核对，核对原归档块摘要，删除已经确认的记录身份；期间新增的晚到记录留待下一次归档。故障与并发测试包括大整数、单位、质量、来源和各版本字段的往返保留、候选记录发生修改、块内容竞争、压缩失败与最终提交失败；记录调整前后受控样本的事务持续时间及样本规模。

River 必须完成实际集成与受控试点，再替换归档、补算和外部投影的通用任务轮询。当前依赖为官方 v0.48.0，先核对正式驱动使用方式，证明任务与业务变更在同一个数据库事务内入队，事务回滚后没有任务、提交前 worker 不能取得任务，并验证重复入队、失败重试、进程中断后的恢复与取消。任务业务身份与现有 outbox 身份保持关联，设备控制继续由控制执行流程承担。维护任务数据的迁移方式必须与 Goose 编号及校验值记录相容，并同步兼容清单。保留 SQLite 开发与测试路径；若正式驱动的限制影响既有行为，应提供可复现试点结果后与主协调者协调方案。

补算恢复以稳定任务代际和运行身份继续，保存完整窗口检查点及固定的历史范围、初始状态关系。当前 `commitEvaluation` 遇到已有inbox会返回空派生输出，因此恢复必须覆盖父计算已经提交而派生子计算尚未完成的间隙：在同一事务保存可恢复的派生结果，或采用等价的完整检查点方案，重复处理能继续后续依赖而保持已提交状态。测试包含同时间戳多输入、跨窗口进度、中断、取消和晚到数据产生新任务代际；`finishReplay` 与算子语义沿用已有实现。

采集、控制、实时分析、补算和归档需要分别明确并发或调度预算；验证在补算或归档积压时，采集和控制能按预算继续处理。任务详情 API 至少提供业务身份、状态、尝试次数、下一次执行时间、失败原因、进度、取消或重试等当前状态允许的操作，同时执行角色、资源范围及版本检查。将前端所需输入输出、状态和示例写入 `tasks-frontend-contract.md`，供前端工程师使用。

PostgreSQL 16 至 18 使用独立旧实例和目标数据库进行受控数据迁移。样本包含旧结构、文档与历史版本、精确数值观测、已有归档、审计链、同步游标及未完成业务；记录迁移命令、版本、样本数量和逐类核对结果，再运行读写与归档回归。第一阶段 CE/Edge 与 PG18 的通信证据可以复用，但必须明确对应数据库、二进制和受测版本。持久服务及其卷保持原有用途，临时实例按名称和唯一 schema 隔离。

文件归属包括 `Platform/internal/store`、新增任务包、`Platform/internal/app/workers.go`、任务 API 与模型，以及相关迁移、任务配置、测试和存储说明。`engine/history.go`、`engine/deferred.go` 及规则测试中的任务调用需要先与规则工程师协调，规则计算语义由规则工程师负责。`app.go`、API 注册、Go 模块依赖、兼容清单及生成契约是共享文件，修改前通知主协调者；每次生成契约保留其他角色已加入的类型和操作。

工作区为 `/path/to/SmartFactory-2026`，用户原有改动已单独保存，禁止回退或覆盖。`docs/` 是现有忽略目录，保留现有发布规则。必要依赖与镜像传输已有授权。Go 使用 `GOTOOLCHAIN=local`、`GOPATH=/private/tmp/smartfactory-evolution-gopath`、`GOMODCACHE=/private/tmp/smartfactory-evolution-gomodcache`、`GOCACHE=/private/tmp/smartfactory-evolution-go-cache`，保持 GOSUMDB 校验。工作卷至少预留 1 GiB，构建及临时数据优先使用 `/private/tmp`。

现有 PG18 临时实例信息位于权限 0600 的 `.local/evolution/pg18-test.json`，读取后在进程内使用，输出中省略凭据。其 `sf_pilot_20261004` schema 和两个原生平台临时数据库正供第一阶段验证，停止或重建容器前先协调。所有验证报告保存实际命令、退出状态、测试数量、源文件与产物摘要，首轮失败保留为独立证据；报告为 `.local/evolution/storage-tasks-verified.json`，最终说明逐项对应 E2-01 至 E2-05 和 E2-09 的任务部分。
