第三阶段文件归属与接口协调

第二阶段十二项已通过专家验证、独立组合审查和主协调复核。第三阶段以 `.local/evolution/phase3-start-baseline.json` 保存的源码与迁移摘要开始，已有迁移00001至00004保持校验值；控制和历史两位工程师同时实施，前端与独立审查按后端交付进度安排。

| 文件或接口 | 维护角色 | 协作方式 |
|---|---|---|
| `internal/control`、控制应用/API、Execution和StepResult、云边回执与协调适配、DataTransfer只读命令查询 | 控制执行工程师 | 控制状态与命令反馈由同一专家维护，向前端提供控制契约 |
| 历史应用/API、独立分析模型、快照/结果存储、独立历史worker | 历史计算工程师 | 固定输入和版本，向前端提供历史分析契约 |
| `app/app.go`、`app/workers.go`、`api/server.go`、`cmd/sf-contracts/main.go`、Go模块 | 控制执行工程师 | 历史专家提供最小注入和注册片段，主协调安排汇合 |
| `store/migration00005.go` | 控制执行工程师 | 保存控制转换与结果依据 |
| `store/migration00006.go` | 历史计算工程师 | 保存独立分析与影子运行结构 |
| `store/migrations.go` | 控制执行工程师 | 集中注册两个新迁移，保留既有编号与摘要 |
| `engine/runtime.go`、`engine/definitions.go`的影子输入钩子 | 历史计算工程师 | 控制条件读取涉及这些文件时，经主协调安排 |
| `tasks/service.go`的Analysis处理器及worker注册 | 历史计算工程师 | 专用analysis队列采用明确预算，既有任务行为继续回归 |
| `store/tasks.go`的analysis任务详情、取消和重试钩子 | 历史计算工程师 | 遵守对象、River行及提交日志锁顺序，保留任务与快照身份 |
| `Frontends`与页面说明 | 后续前端交互工程师 | 按两份专家契约实现，并用实际后端完成浏览器流程 |
| 计划、团队、验收与证据汇总 | 主协调者 | 审查专家交付，记录未决事项和复查结果 |

输入传播需覆盖 `app/workers.go` 的strategy与engine两路持久投递，以及原生回调中的Process入口。ProcessStrategies对迟到或过期点提前返回，ProcessCalculations中的历史分支也可能提前返回或转交正式补算；影子专家需按约定输入范围处理这些分支，并在同一观测经两个入口时按身份与修订去重。正式补算产生的历史处理保持其原用途，影子运行保存自己的状态、结果及动作意图。

控制取消后的未知设备结果继续保留原命令核对及后续反馈；较早或重复云边回执按来源版本判断，本地文档版本独立递增。人工核对及恢复采用当前身份、授权、对象版本和执行权，自动恢复继续遵守未知结果的既有处理规则。具体字段与允许操作以两位专家提交的契约和实际验证为准。

云端人工取消、核对与恢复通过持久操作下行至边缘处理，反馈经既有云边回执返回。主协调已确认该实现属于本阶段两类入口的完整流程；控制专家负责双应用的身份、期限、版本与回执验证，前端负责异步等待、失败原因和实际执行结果的呈现。

资源预算沿用第二阶段：两个专家同时运行，PostgreSQL每个测试应用最多三个连接、一个空闲连接，使用独立schema并将包并行度设为一；实际NATS和大型竞态检查提前由主协调安排时段。临时产物保存在允许目录，工作卷保留至少1 GiB；验证完成后关闭自建服务并保存摘要与运行证据。
