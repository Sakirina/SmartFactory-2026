# 存储与后台任务实施记录

本轮完成 E2-01 至 E2-05 以及 E2-09 的后台任务部分，当前为对应实现与验证完成、等待主协调者验收。完整命令、退出状态、逐项条件跳过、原始失败、源码摘要和日志索引位于 `.local/evolution/storage-tasks-verified.json`；可复核日志已复制到 `.local/evolution/storage-evidence/`，独立 PostgreSQL 迁移复核另见 `.local/evolution/postgres-migration-root-review.json`。

E2-01 使用 PostgreSQL 16.15 独立临时实例与 PostgreSQL 18.6 独立目标库执行 custom 格式导出和恢复。样本包含两个业务文档、四条历史、64 条热观测、一个包含 64 条观测的归档块、三条签名审计及检查点、同步游标 21、等待投递记录与 inbox；九类记录在应用迁移前的行数和 SHA-256 全部一致。启动后原有历史和 128 条观测的完整字段校验通过，旧任务与 outbox 被 River 承接，新增读写、64 点归档和审计链从三条延长至四条也通过。专用 PostgreSQL 16 容器已清理，目标验证库与原 PG18 容器继续保留。部署清单锁定 PostgreSQL 18.6，独立 `*-pg18` 卷挂载 `/var/lib/postgresql`；实际实例数据目录为 `/var/lib/postgresql/18/docker`。安装与备份文档已经补充大版本迁移流程。

E2-02 的业务事务按对象取得锁，授权、集合成员和依赖读取使用共享锁，成员变更及对象写入使用相应排他锁；提交日志锁仅覆盖最终同步序号与审计追加。真实 PostgreSQL 证明两个独立业务回调同时运行，18 次同对象递增的回调各运行一次，不存在身份的竞争得到一次成功和一次冲突；迟开始提交的日志序号不会越过已经对外可见的游标。独立 SaveDraft 调用通过数据库 UPDATE 屏障确认共享人员、授权和资产读取时仍能并行，实际 HTTP 死锁返回一个 200 和一个 409。finalize 失败共同回滚文档、历史、inbox、outbox、同步、审计和正式 River 记录，分区创建、退休与晚到写入竞争也已验证。

实际领域存储接口位于 `Platform/internal/application/repositories.go`：`Definitions.Store` 使用 `DefinitionRepository`，`Tasks.Store` 使用 `TaskRepository`，授权读取使用 `DocumentQueries`；发布事务使用 `definitioncommit.Repository`。worker 在 `Platform/internal/tasks/repository.go` 声明 `Repository`，Service 字段通过它调用归档调度、补算失败保存和投影完成，构造时的 Backend 增加正式 River 客户端工厂。授权版本检查 SQL 位于 `store/revisions.go`，worker 的 SQL 与驱动工厂位于 `store/task_runtime.go`。这些接口已经用于实际应用路径，控制与其他历史分析模块留待对应阶段沿用。

E2-03 在写入事务外读取候选、编码压缩并完整解码校验，提交时比较原始身份、时间、JSON 和原归档块，再精确删除已经确认的候选。测试覆盖晚到观测保留、候选变化、块新增／修改、编码失败和最终提交失败，保留大整数、单位、质量、来源与全部版本字段。相同规模的两个序列各有 1536 点，约 2.4 MiB 原文；最后一次独立样本中旧写入事务为 126.803417 毫秒，新事务外准备为 97.76475 毫秒，精确 CAS 写入事务为 109.195292 毫秒，包含故意插入晚到数据的新流程总耗时为 209.604334 毫秒。报告同时保留其他运行样本，供比较仪器开销与资源竞争；这些单次计时用于说明工作分布，性能结论需要在统一负载下统计分布。

E2-04 使用官方 River v0.48.0 的 database/sql 与 SQLite 驱动。任务和业务、outbox 使用同一个事务；实际 worker 验证回滚无任务、提交前不可获取、提交后执行一次、重复身份保留一次入队、失败重试和取消。启动依次迁移 Goose 至 3、River 至 8、Goose 至 4；原迁移 1 至 3 的 SQL／Go 文件 SHA-256 与第一阶段一致，River 完成后 bridge 失败的再次启动也能恢复。归档、补算和外部投影由 River 执行，设备控制保留现有执行流程。

补算首次执行保存选定定义、设备、固定历史起止时间与起点之前的状态快照，游标仅在完整窗口完成后推进，计算输出回执与 inbox／状态一起提交。真实子进程 SIGKILL 后由官方 River rescuer 执行第二次尝试，同一 task、River、业务和 replay 身份继续工作；同一时间戳的多个输入、父计算已经提交但子计算尚未完成、跨窗口检查点均已覆盖。取消和新代际保留此前提交结果。逐点结束后进入 rollups 阶段，每个汇总写入事务检查业务版本；跨日故障留下的 15 条汇总在取消后继续保留，同一身份重试后完成 24 条汇总，正式状态版本与派生输出回执保持一致。

旧 `POST /jobs/{id}/retry` 已使用 Tasks 应用用例，保持 HTTP 202 与 Job 返回形状。已有映射继续原身份、游标和汇总阶段；迁移前无映射的 failed Job 通过授权版本校验、业务更新、任务映射、River 入队和审计的共同事务完成一次承接，缺少固定快照的旧任务在首次执行时建立恢复记录。测试通过旧 HTTP 入口恢复逐点与汇总两种中断，覆盖角色与全部资源授权、授权集合／定义版本变化、审计失败回滚、过期 River 记录 404，以及旧／新入口并发只成功一次。真实 PostgreSQL 的并发请求也得到一个成功和一个 409。

E2-05 的预算按进程计算：采集并发 4、每批 10000 点、30 秒；控制所有入口共用 3 个完整 Run 生命周期的并发预算；实时分析与策略各一条消费流程；补算并发 1、30 秒；归档并发 1、每块 4096 点与 8 MiB、每次最多 16 块和 5 秒；外部投影并发 2、15 秒。实际 HTTP 审批／下发、后台消费与两个自动控制共享预算，第四个等待者可取消，补算和归档积压期间采集继续提交。PostgreSQL 每批 10000 点同时生成 30000 条 outbox 和 10000 条 River 任务，重复批次保留原任务数量。

E2-09 的任务 API 提供业务关联、River 状态、尝试次数、时间、错误、进度、阶段、恢复身份和服务端允许操作；取消与重试检查角色、全部资源、授权版本、任务版本和实际 River 状态。前端约定详见 [任务接口](tasks-frontend-contract.md)。OpenAPI 包含 71 个 Schema 与 56 项操作，Go 导出 JSON Schema／OpenAPI，前端用正式 openapi-typescript 生成类型。任务等待和执行、归档准备和提交均有固定 span 名称，业务身份在追踪属性中，等待指标只按有限队列名分组。

普通全量与 PostgreSQL 专项分别记录受测源码，race 首轮两个大样本触发了正式的 5 秒归档与 30 秒采集超时；原始失败和实际耗时均保留，生产预算保持原值。后续 race 检查明确排除这两个大样本，保留其余并发与恢复用例。普通套件中的条件跳过逐名标明 PostgreSQL 补验、其他角色证据、子进程辅助调用和仍需主协调者复核的外部专项，空测试包与跳过的测试函数分别统计。
