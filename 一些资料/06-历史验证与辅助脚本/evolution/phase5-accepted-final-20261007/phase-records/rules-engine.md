# 第二阶段规则计算实现与验证

本记录覆盖 E2-06、E2-07、E2-08，以及 E2-09 的连续模拟服务与 API。规则实现已经通过本轮验证，阶段验收由主协调者依据证据确认；E2-09 的任务详情与页面由对应专家继续处理。机器可检查的命令、退出码、测试结果、计数和文件摘要保存在 `.local/evolution/rules-verified.json`，前端请求及响应说明见 [规则接口](rules-frontend-contract.md)。

## 发布和计划身份

`internal/rulecore.Compile` 依据 `model.NodeCatalog()` 校验定义、节点、端口、参数、图依赖与表达式，产生 `model.ExecutionPlan`。计划保存拓扑排序后的节点、类型化参数、已解析表达式树、选择器、策略、输出和依赖引用。图最多包含 128 个节点、512 条连接；表达式最多 4096 字节、256 个操作节点和 32 层嵌套，表达式错误附带节点 ID 与 `params.code`，参数错误附带节点 ID 与参数名。

`content_sha256` 覆盖去除 `execution_plan` 字段后的完整定义 JSON，计划身份为 `<definition_id>:<definition_version>:<content_sha256>`。`sha256` 覆盖计划自身除摘要字段外的 JSON；加载和导入同时检查格式版本、定义身份、内容摘要与计划摘要。计划作为 `compiled_plan` 文档保存，初次版本为 1；相同内容再次保存沿用已有记录，内容冲突则返回错误。

正式发布通过 `application/definitioncommit.Commit`：设置发布版本与生效时刻、编译计划，然后在同一事务内复核已授权的对象和集合版本，准备依赖计划，写入定义、计划、目录、草稿修订、审计与两个后续投递任务。缺失依赖、存储失败或审计失败使事务回滚。发布返回的定义携带同一计划，供云边同步沿用发布节点形成的身份。

应用启动在启动工作协程之前执行 `PreparePublishedPlans`，扫描已发布定义的历史版本。没有计划的旧定义在此阶段完成编译；旧定义语法或依赖无效时，保存 `plan_issue` 并隔离该版本，其余有效版本继续准备。语义错误包括 `definition_compilation`、`dependency_unavailable` 和 `dependency_cycle`。存储读写失败、取消，以及已有计划损坏会返回启动错误。

云边元数据导入先在事务中保存整批来源文档，再准备计划，因此同批次中位于后面的依赖也可供前面的消费者使用。依赖选择采用消费者定义生效时刻之前的历史版本，嵌套依赖采用同一参照时刻。旧格式定义缺失依赖时保留隔离诊断，后续批次到达依赖后通过 `RetryIssues` 再次准备并清除已恢复诊断；新格式携带的计划发生格式或摘要错误时，整批导入回滚。来源定义的版本、内容和同步游标仍按既有导入事务提交，隔离定义暂停向原生规则桥投递。

`GET /api/sf/v1/definitions/{id}/plans` 返回历史发布版本的 `prepared`、`unprepared` 或 `isolated` 状态，以及内容、计划摘要和隔离原因。API 在返回结果前检查每个历史定义及其中全部资源引用的读取权限。

## 计算输入和状态

实时计算、定时计算、连续模拟和补算最终调用 `rulecore.Execute(ctx, plan, frame)`。计算核只处理给定计划与 `Frame`，其中明确包含当前观测、窗口、其他输入字段、逻辑时刻、新鲜度参照时刻、阈值、计算实体、初始节点状态、资产版本与历史标记；运行层负责查询数据库和构造这些输入。`Execute` 复制输入及嵌套 JSON 状态，每次计算返回自己的值、状态和节点轨迹，调用者修改一次结果不会影响下一次运行。

实时运行从持久计划与进程缓存中加载计划，逐条观测和定时触发继续复用表达式树。服务重建并重新打开数据库后，启动准备复用同一持久计划。公开诊断 `Evaluate` 与草稿模拟在各自入口编译，连续模拟每个请求编译一次，随后全部点共用该计划。

观测的原始值、质量、单位、来源序号、设备时间和版本字段随输入保存。窗口按 `(observed_ms - window_ms, observed_ms]` 选取，并按照设备时间、来源序号、观测 ID 排序；不设窗口时使用当前点。数值汇总采用 `pkg/precise`，只有 `GOOD` 且可解析为数值的观测参与数值统计。窗口的输入身份和质量统计随结果返回，`aggregate` 节点遇到参与窗口中的不同非空单位时返回错误。

JSON 数值使用 `json.Number` 解码。有理数算术在表达式内部保留整数精度，整数结果以 JSON 数值输出；非整数表达式结果与平均值转换为 float64。`round` 按距离最近的整数取值，恰好位于中点时向远离零的方向取整。数字文本最多 768 字节，十进制指数在 -308 至 308 之间，分子与分母最多 4096 位；字符串值不会自动转换为数字。样本验证了 `9007199254740993 + 1 = 9007199254740994`，以及两个 `9007199254740993` 的窗口和为 `18014398509481986`。

计数器状态采用 int64。`delta` 模式要求输入为 int64 范围内的整数，拒绝小数、数字字符串和越界数值；累加前检查溢出。非 `GOOD` 观测保持已有计数。`rising` 模式只在布尔值由 `false` 变为 `true` 的时候增加一次，其他模式按目录参数处理。

逻辑时刻用于持续时间、防抖和节点状态时间，设备时间用于窗口及资产版本选择。实时计算默认以服务时钟判断新鲜度，历史补算默认使用观测时刻，定时计算使用本次定时时刻。新鲜度判断为 `0 <= freshness_at_ms - observed_ms <= freshness_ms`，阈值优先取规则参数，再取设备采样间隔三倍与 5000 ms 中的较大值。资产层级按观测时刻读取历史版本，因此迁移后的设备不会改变此前观测的归属。

`policy.timeout_ms` 限制整张图的一次执行，默认 100 ms；多个表达式共用同一个 deadline。每个表达式另外具有操作数、深度和数值长度预算。测试在第一条表达式完成后耗尽同一上下文预算，验证第二条表达式不会获得新的图执行时间。

## 连续模拟与历史补算

`POST /api/sf/v1/drafts/{id}/simulate` 支持 `points`、`history`、`initial_state`、`clock`、`order`、`asset_versions`、`timeout_ms` 与 `expected_version`。初始状态按照实体 ID、节点 ID 两层组织，不同实体分别延续各自状态；选择器指定 `asset_id` 时使用资产 ID 作为计算实体。每条已执行输入进入后续窗口，`event_time` 按设备时间、来源序号、ID 排序，`provided` 保留请求顺序。响应中的 `input_index` 对应请求数组位置。

明确提供 `history: []` 或 `asset_versions: []` 使用空快照，省略字段则查询所需的数据库内容；Go 请求序列化也保留明确的空数组。实际历史、资产快照、历史摘要与输入摘要随响应返回，可以作为下次请求输入复现计算。输入摘要覆盖计划身份、顺序、时钟、规范化观测、历史、初始状态与资产版本。`clock.at_ms`、`step_ms`、`freshness_at_ms` 和 `freshness_ms` 可分别固定执行时钟、递增量、新鲜度参照和阈值。

每个请求最多 1000 条连续观测、40000 条历史、40000 项资产版本，整体预算默认及上限为 5000 ms；调用方可减少 `timeout_ms`。整体预算覆盖准备、查询和逐点计算，并与单图预算共同作用。API 检查输入、历史、初始状态实体、资产及祖先引用的读取权限；草稿修订发生变化时返回 409。响应提供逐点结果、节点轨迹、最终状态、实际草稿修订、计划身份、内容与计划摘要、采用的时钟和快照。原有单点 `point` 请求继续返回 `Evaluation`。

模拟的全部状态保存在请求内及响应中，测试逐项检查 `engine_state`、`recompute_state`、告警、执行任务与持久计划均未产生写入。输入缺失、重复身份、超出预算、取消和资源权限不足均经过对应样本验证。

现有补算继续使用独立的运行状态，完成后由 `finishReplay` 合并计数和告警投影，这一行为沿用本轮主协调者确认的既有语义。回归样本中补算完成后正式计数为 7，下一条实时输入后为 8；历史告警保留已确认状态，当前告警仍指向当前活动事件。第三阶段独立回放与影子计算使用各自运行身份及保存范围，由后续相应工作实现。

## 目录、契约与证据

`model.NodeCatalog()` 集中提供 12 类内建节点的类型、名称、适用定义、输入输出端口、参数类型、必填条件、默认值、枚举、范围、单位、帮助与状态属性。后端编译校验直接读取同一目录，`ParameterSchema` 和 `Node.schema.json` 的条件参数约束由该目录生成；`GET /api/sf/v1/rule-nodes` 供编辑器及工具说明读取。契约生成与校验确认 67 个 Schema、51 项 API 操作和 24 个可编辑定义样本。

最终 Platform 命令为 `go test -count=1 -json ./...`，记录 188 项通过、0 项失败、7 项依赖环境跳过，统计包含 Go 子测试。PostgreSQL 18 专项通过隔离的临时 schema 实测，1 项通过、0 项跳过：8 个并发相同计划写入仍保持文档版本 1，同批依赖成功准备，损坏计划导致定义、历史、同步游标与审计一起回滚。该专项使用至多 3 个业务连接及 1 个 schema 管理连接，结束后删除测试 schema。

编译和解析计数来自实际执行中的原子计数器。连续模拟 3 点记录编译 1 次、表达式解析 1 次、执行 3 次；实时 20 点记录编译 0 次、解析 0 次、执行 20 次；实时与定时场景记录编译 0 次、解析 0 次、执行 76 次；补算记录编译 0 次、解析 0 次、执行 3 次。序列化计划连续执行 51 次与重新打开数据库后的计划准备也均未增加编译、解析计数。

前任交接时的 8 项失败来自绕过准备阶段直接安装定义的测试夹具及原生发布进度夹具，现已补充显式准备，并在直接安装规则的 `sf-site-fixture` 入口将计划与定义一起提交。本轮新增窗口测试曾因 1970 年测试时刻被当前保留策略清除数据而失败，已为该夹具提供明确的服务时钟；新增发布断言曾因未使用的导入产生编译失败，删除多余导入后全量回归通过。这些中间失败及对应命令保留在证据记录中。
