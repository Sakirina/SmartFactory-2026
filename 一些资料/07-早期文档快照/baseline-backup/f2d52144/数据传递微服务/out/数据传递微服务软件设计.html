1. 设计目标与边界

数据传递微服务定位为智能工厂物联网平台的边缘侧通信中间件，负责把南向设备协议中的原始数据转为统一的 DeviceMessage，并通过北向接口交付给边缘控制节点内的上游微服务；同时承接上游下行指令，经过反向转换后写入或调用目标设备。

本设计文档面向即将开始的开发工作，重点说明代码结构、运行时组件、接口实现方式、技术栈选择与工程约束。需求分析文档中的业务范围应作为边界参考，但开发阶段需要保留架构判断：凡是跨服务职责尚未对齐、性能目标缺少测试依据、控制指令存在安全风险的内容，均应进入设计确认清单，不宜在首版开发中默认固化。

1.1 核心职责

数据传递微服务承担以下职责：

职责 设计含义 主要模块
南向协议接入 连接 Modbus、OPC-UA、MQTT、BACnet、HTTP 等设备或协议网关 Connector Runtime
数据归一化 将协议原始数据转换为统一 DeviceMessage Converter Engine
北向交付 通过 gRPC 或 MQTT 将消息交给上游服务 Northbound Adapter
下行指令执行 将标准指令路由到设备并追踪执行结果 Command Router、Ack Tracker
配置热加载 承接设备注册微服务推送的设备、Connector、策略配置 Config Manager
本地缓冲与续传 方案B下保存北向断连期间的数据并恢复补发 Buffer Store、Replay Worker
可观测性 暴露健康检查、指标与结构化日志 Observability

1.2 职责边界

本微服务只处理通信、转换、路由与短期缓冲。设备台账、设备标签语义、准入审批、数据清洗、业务聚合、规则判断、策略编排、安全联锁等职责由其他服务或硬件系统承担。尤其是 PLC、SIS、ESD 等安全联锁路径，不应经过本微服务转发；涉及人员安全、设备保护和强约束工艺逻辑的控制链路，需要保留独立硬件或专用控制系统。

自动发现设备只产生“候选设备发现事件”。数据传递微服务不得因为发现了设备就直接纳入正式采集，必须等待设备注册微服务确认并推送正式配置。

2. 总体技术选型

2.1 基准技术栈

类别 基准选型 说明
实现语言 Go 数据传递场景以 I/O 并发、网络连接和边缘部署为主，Go 的 goroutine、channel、交叉编译和单二进制交付能力适合首版工程化
数据模型 Protocol Buffers v3 与接口文档保持一致，提供强类型结构、字段编号兼容与多语言生成能力

方案B北向通信 MQTT v5.0，兼容 v3.1.1 适用于跨网络部署，支持 QoS、User Properties、遗嘱消息与网关实例聚合

容器与部署 单二进制 + 可选容器镜像 兼顾工控机裸机部署、容器化部署和信创适配

2.2 选型约束

Go 作为基准语言，并不意味着所有插件都必须进程内实现。主进程应使用 Go 完成核心调度、接口、缓冲、指标与内置协议 Connector；第三层纯自定义插件可提供两种方式：可信插件以进程内组件注册，不可信或复杂插件以独立进程 sidecar 方式接入。

Protobuf 是北向和内部统一模型的主格式，但南向设备协议可以按实际设备能力选择 JSON、寄存器表、OPC-UA Node、二进制帧等格式。Connector 与 Converter 负责协议侧格式到 DeviceMessage 的转换，核心管线不直接依赖南向协议细节。

3. 运行模式设计

3.1 方案A：嵌入式部署

方案A适用于数据传递微服务与数据处理、规则缓存、命令编排、设备注册等服务部署在同一边缘控制节点内的场景。北向接口使用 gRPC，默认监听 localhost:50051，管理接口默认监听 :8080。

方案A中北向通信为本地调用，首版可以不启用持久化缓冲。内部仍应保留队列和背压控制，因为上游 gRPC stream 消费变慢时，消息生产速度仍可能超过消费速度。此时可以使用应用层背压控制 Connector 采集节奏，防止内存无限增长。

3.2 方案B：分体式部署

方案B适用于数据传递微服务运行在边缘网关设备上，通过网络连接边缘控制节点的场景。北向接口使用 MQTT，Topic 按 dt/v1/{direction}/{gatewayId}/{messageType} 命名，Payload 使用 Protobuf 二进制编码。

方案B必须启用本地缓冲、续传限速和两阶段确认。实时数据与历史补发数据应拆成两条逻辑通道：实时通道负责当前采集消息，续传通道按时间次序读取缓冲中的 pending 记录并批量发送。两条通道共享北向连接状态、发送速率限制和错误处理策略。

3.3 运行模式选择

运行模式由配置项 deployment.mode 控制：

deployment:
  mode: embedded # embedded | split
gateway:
  id: edge-gateway-001
northbound:
  grpc:
    listen: "127.0.0.1:50051"
  mqtt:
    broker: "ssl://edge-controller:8883"
    client_id: "gateway-edge-gateway-001"
management:
  listen: "0.0.0.0:8080"

首版开发应避免让同一实例同时开启完整 gRPC 与 MQTT 北向交付路径。可以保留管理端和配置校验能力，但数据上报与下行命令应根据运行模式选择一个主通道，以减少状态分裂。

4. 总体架构

微服务运行时建议划分为十个核心模块：

Bootstrap
  └─ Runtime Supervisor
       ├─ Config Manager
       ├─ Connector Runtime
       │    ├─ Built-in Connectors
       │    └─ External Plugin Bridge
       ├─ Converter Engine
       ├─ Device Registry Cache
       ├─ Report Strategy Engine
       ├─ Backpressure Controller
       ├─ Northbound Adapter
       │    ├─ gRPC Adapter
       │    └─ MQTT Adapter
       ├─ Command Router
       ├─ Buffer Store / Replay Worker
       └─ Observability

4.1 Bootstrap

Bootstrap 负责读取本地配置、解析命令行参数、应用环境变量覆盖、初始化日志、启动管理端口并创建 Runtime Supervisor。配置加载应按以下次序处理：

  1. 默认配置；
  2. YAML 配置文件；
  3. 环境变量；
  4. 命令行参数；
  5. 设备注册微服务推送的运行时配置。

后来的配置来源覆盖前面的配置来源，但运行时推送配置必须经过校验、差异分析和变更日志记录。

4.2 Runtime Supervisor

Runtime Supervisor 是主流程协调器，负责各模块生命周期管理。它不宜成为“所有状态的巨型仓库”，否则后续插件扩展、配置热加载和错误隔离都会变得困难。更合适的方式是让 Supervisor 负责调度和状态汇总，让业务状态分别保存在 Connector Runtime、Device Registry Cache、Buffer Store、Ack Tracker 等专门模块中。

Supervisor 需要提供以下能力：

能力 说明
启动编排 按配置启动 Connector、北向适配器、管理接口、缓冲与续传任务
停止编排 接到退出信号后取消 context，等待 Connector 和后台任务归还资源
异常隔离 单个 Connector 异常时只重启或标记该 Connector
运行状态汇总 聚合设备数、Connector 状态、队列容量、北向连接状态等指标
热加载调度 接到配置变更后选择局部更新、Connector 重载或拒绝变更

4.3 Connector Runtime

Connector Runtime 负责实例化、启动、停止和重载协议 Connector。每个 Connector 实例必须具备独立生命周期：initializing、running、error、stopped。单个 Connector 异常不得阻断其他 Connector 的数据采集和指令执行。

内置 Connector 的首版范围建议为：

协议 首版能力
Modbus TCP 读寄存器、读状态位、写寄存器、写线圈、基础重连
MQTT Device 订阅设备遥测、状态、事件，发布下行指令，处理设备回执
OPC-UA 可作为首版后续能力；若工期允许，优先支持 Read、Write、Subscription

BACnet、HTTP、S7、串口 RTU、自定义 TCP 等协议可通过同一接口扩展。首版不宜一次覆盖过多协议，否则 Converter、配置模型和测试夹具都难以充分验证。

Connector 的开发契约以接口文档中的 Go 接口为基础，建议在代码中拆成三类接口：

type Connector interface {
    Init(config ConnectorConfig) error
    Start(ctx context.Context, upstream chan<- *DeviceMessage) error
    SendCommand(ctx context.Context, cmd *DeviceMessage) (*CommandResponsePayload, error)
    ReloadConfig(config ConnectorConfig) error
    Stop() error
    Status() ConnectorStatus
    Devices() []DeviceInfo
}

如果某些协议天然只支持上行采集，不支持下行控制，也应显式返回 DT-CMD-003 或能力不足的错误，不应让 Command Router 猜测协议能力。

4.4 Converter Engine

Converter Engine 负责协议原始数据与 DeviceMessage 的双向转换。它是本微服务区别于 ThingsBoard IoT Gateway 的关键模块：同一个设备配置应同时描述上行解析和下行编码，保证数据点命名、单位、值转换、寄存器地址或节点地址的映射关系一致。

建议配置结构包含以下内容：

devices:
  - device_id: sensor-001
    device_name: "车间A温度传感器"
    device_type: temperature_sensor
    tags:
      workshop: "车间A"
      line: "产线3"
    address:
      unit_id: 1
    datapoints:
      - key: temperature
        source: "holding_register[0]"
        type: int16
        transform: "value * 0.1"
        unit: "deg C"
        writable: false
      - key: setpoint
        source: "holding_register[9]"
        type: int16
        transform: "value * 0.1"
        inverse_transform: "value / 0.1"
        unit: "deg C"
        writable: true

上行转换流程：

  1. Connector 读取原始帧或协议对象；
  2. Converter 定位设备与数据点配置；
  3. 执行类型解析、字节序处理、表达式转换、单位标注；
  4. 合并 Connector 默认标签与设备标签；
  5. 生成 DeviceMessage，填充 messageId、timestamp、device、type 和 payload；
  6. 转换失败时记录 DT-CVT-001，跳过单条异常数据，不阻塞同一 Connector 的后续数据。

下行转换流程：

  1. Command Router 根据 deviceId 定位 Connector 和设备配置；
  2. Converter 根据 ControlPayload、ParamUpdatePayload 或 QueryPayload 定位可写数据点或动作映射；
  3. 执行反向表达式、类型编码、协议帧构造；
  4. Connector 发送协议帧或调用协议服务；
  5. Ack Tracker 记录执行状态并生成回执。

表达式引擎需要限制能力范围：只允许无副作用表达式，不允许文件、网络、系统调用等能力。表达式编译结果应缓存，避免每条数据重复解析。

4.5 Device Registry Cache

设备注册微服务是设备元数据与标签的权威来源。数据传递微服务本地只维护运行时缓存，用于路由、标签填充和状态查询。

缓存内容包括：

字段 来源 用途
deviceId 设备注册微服务 指令路由、消息来源
deviceName 设备注册微服务 运维展示
deviceType 设备注册微服务 订阅过滤、指标分组
connectorId 配置推送 定位 Connector
protocol Connector 配置 协议统计
tags Connector 默认值 + 设备级覆盖 上游过滤、聚合维度
state Connector Runtime 在线、离线、异常状态
lastSeen Connector Runtime 设备活跃度判断

标签合并规则为设备级覆盖 Connector 级默认值。微服务只透传标签，不解释标签语义，也不做标签白名单限制。

4.6 Report Strategy Engine

上报策略只作用于 TELEMETRY 消息，STATUS、EVENT、CMD_RESPONSE 必须即时进入北向通道。策略模式包含：

模式 行为
ON_RECEIVED 数据到达即交付
ON_CHANGE 值发生变化且超过死区后交付
ON_REPORT_PERIOD 按周期交付最新值
ON_CHANGE_OR_REPORT_PERIOD 变化时立即交付，无变化时按周期交付最新值

策略配置优先级为数据点级、Connector 级、全局默认。实际实现时，应将策略状态按 connectorId + deviceId + datapointKey 建立索引，保存上次交付值、上次交付时间和被过滤计数。策略变更热加载后，需要谨慎处理历史状态：模式变化时可以重建相关 key 的策略状态，避免旧状态影响新策略。

4.7 Backpressure Controller

背压控制负责在上行生产速率高于北向消费速率时保护进程内存和缓冲存储。建议设置三级水位：

水位 触发条件 行为
观察水位 队列使用率 >= 60% 记录指标，增加日志采样
控制水位 队列使用率 >= 80% 启动配置的背压策略
恢复水位 队列使用率 <= 50% 解除背压，记录恢复事件

背压策略可选：

策略 实现方式 风险
BP_BLOCK 暂停或延迟 Connector 向上行队列写入 可能导致采集周期漂移
BP_DROP_OLDEST 淘汰队列里最早的遥测消息 需要记录丢弃范围，并保持状态、事件、回执优先
BP_DEGRADE 临时调低采集频率或跳过部分轮询周期 需要 Connector 支持动态采集节奏

STATUS、EVENT、CMD_RESPONSE 的优先级应高于普通遥测。对于控制回执，不应因为遥测积压而延迟到上游误判超时。

4.8 Northbound Adapter

Northbound Adapter 负责将内部 DeviceMessage 转为部署模式对应的北向交付方式。

gRPC Adapter 实现：

接口 设计说明
SubscribeTelemetry 使用服务端流式响应，只发送 TELEMETRY
SubscribeEvents 发送 STATUS、EVENT、CMD_RESPONSE
PullMessages 方案A专用：从内存环形缓冲中拉取近期消息，用于上游服务重启后追赶最近 N 分钟的数据，不涉及持久化；方案B下不使用——积压数据由 Replay Worker 通过 MQTT 补发，上游重新订阅即可
SendCommand 同步等待执行结果
SendCommandAsync 立即返回接纳结果，执行回执经事件流推送
PushDeviceConfig 承接设备注册微服务配置推送
ListDevices 返回本地设备缓存状态
GetMetrics 返回结构化指标快照

MQTT Adapter 实现：

Topic Payload 设计说明
dt/v1/up/{gatewayId}/telemetry DeviceMessageBatch 批量遥测，QoS 1
dt/v1/up/{gatewayId}/status DeviceMessageBatch 状态消息，QoS 1
dt/v1/up/{gatewayId}/event DeviceMessageBatch 事件消息，QoS 1
dt/v1/up/{gatewayId}/cmd-response DeviceMessageBatch 指令回执，QoS 2
dt/v1/up/{gatewayId}/discovery 待设备注册服务确认 自动发现候选设备
dt/v1/down/{gatewayId}/command DeviceMessage 下行指令，QoS 2
dt/v1/down/{gatewayId}/config DeviceConfigUpdate 配置热加载，QoS 2
dt/v1/meta/{gatewayId}/devices ListDevicesResponse 当前设备列表快照（retained），QoS 1，网关定期发布
dt/v1/meta/{gatewayId}/metrics 指标快照 周期发布，QoS 0
dt/v1/meta/{gatewayId}/lwt 离线状态 Broker 遗嘱消息

接口文档要求 MQTT 下行指令使用 QoS 2。开发时仍需要额外实现指令幂等保护：QoS 2只能约束 MQTT 传输层的一次投递语义，无法保证设备侧动作不会因重试、重连、设备自身回执异常而重复执行。command_id 必须进入 Ack Tracker 和 Connector 执行去重逻辑。

4.9 Command Router 与 Ack Tracker

Command Router 负责根据 DeviceMessage.device.deviceId 定位目标 Connector，校验设备在线状态、指令类型、协议能力和超时设置。若设备离线、Connector 不存在、Connector 状态异常或协议不支持该指令，应立即返回 REJECTED 或 FAILURE，并记录错误码。

command_id 去重（FR-S-012, DT-CMD-005）： Command Router 在分发指令前，必须检查 DeviceMessage.command_id 是否已在 Ack Tracker 中存在。已存在的 command_id 应直接返回已有结果或 REJECTED（附原因"duplicate command"），不得重复下发至 Connector。command_id 位于 DeviceMessage 信封层（字段编号 6），由调用方分配并保证全局唯一，与 message_id（消息传输追踪）职责分离。这是对 MQTT QoS 2 传输层语义的应用层补充——即使传输层保证了"精确一次投递"，设备侧重连、Broker 故障恢复等场景仍可能产生重复指令。

Ack Tracker 负责维护下行指令生命周期：

PENDING -> SENT -> DELIVERED -> EXECUTED
                         └──-> FAILED
                         └──-> TIMEOUT

建议将状态记录保存在内存索引中，并按 command_id 设置 TTL。方案B中，如果需要在服务重启后追踪未完成指令，需要额外讨论是否将 Ack Tracker 持久化；当前需求文档要求断连期间下行指令直接返回设备不可达，未要求本地排队，因此首版可以不持久化未完成指令。

同步指令 SendCommand 的响应应来自实际执行结果或超时结果。异步指令 SendCommandAsync 只返回接纳结果，最终结果通过 CMD_RESPONSE 上行消息交付。

4.10 Buffer Store 与 Replay Worker

方案B下，本地缓冲采用两阶段确认：

  1. 上行消息生成后先写入 Buffer Store，状态为 pending；
  2. Northbound Adapter 批量读取 pending 消息并发送；
  3. Broker 确认或发送成功后标记为 completed；
  4. 清理任务按批次删除 completed 记录；
  5. TTL 到期或容量超限时按策略清理，并记录丢弃范围。

SQLite 表结构可按以下方向设计：

CREATE TABLE outbound_messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  message_id TEXT NOT NULL,
  batch_key TEXT NOT NULL,
  message_type INTEGER NOT NULL,
  device_id TEXT NOT NULL,
  connector_id TEXT NOT NULL,
  created_at_ms INTEGER NOT NULL,
  status TEXT NOT NULL,
  payload BLOB NOT NULL,
  retry_count INTEGER NOT NULL DEFAULT 0,
  last_error TEXT
);

CREATE UNIQUE INDEX idx_outbound_message_id ON outbound_messages(message_id);
CREATE INDEX idx_outbound_pending ON outbound_messages(status, created_at_ms);
CREATE INDEX idx_outbound_device ON outbound_messages(device_id, created_at_ms);

实时通道和续传通道都应通过统一发送器进入 MQTT Adapter，避免 QoS、限速、日志和错误处理分裂。续传通道需要支持 buffer.resume_rate_limit 和 buffer.resume_batch_size，防止网络恢复后产生流量尖峰。

5. 数据模型设计

5.1 DeviceMessage

代码中的 Protobuf 定义应与接口文档保持同源维护，建议放在 proto/datatransfer/v1/datatransfer.proto。所有内部模块使用生成后的强类型结构，不在核心管线里传递松散 JSON。

关键字段约定：

字段 设计约束
message_id 使用 UUID v7 或等价的时间有序 ID；用于去重、日志追踪和缓冲唯一键
timestamp 使用 Unix 毫秒；设备时间不可信时使用采集时间，并在 metadata 标注时间来源
direction 上行消息为 UPSTREAM，下行指令为 DOWNSTREAM
device 本消息关联的设备：上行表示来源设备，下行表示目标设备。字段名 device 语义中立，无方向歧义
command_id 下行指令的唯一标识，由调用方分配。上行 CMD_RESPONSE 回填原指令 ID，其他上行消息留空。与 message_id（消息传输追踪）职责分离
type 与 payload oneof 必须匹配
metadata 保存采集时间来源、协议补充信息、原始质量标识等扩展字段

5.2 数据质量与时间戳

数据点级 quality 必须由 Converter 填充。转换失败、取值越界、设备时间异常等情况不能简单丢弃；可转换但可信度不足的数据应标记为 UNCERTAIN，无法转换的数据记录 DT-CVT-001 后跳过。

时间戳处理建议：

场景 处理方式
设备提供可信时间 使用设备时间，metadata 标注 time_source=device
设备未提供时间 使用采集时间，metadata 标注 time_source=collector
设备时间明显异常 使用采集时间，数据质量可标记 UNCERTAIN

5.3 Protobuf 兼容策略

字段编号一旦发布不得复用。删除字段时应使用 reserved 标记。新增字段允许向后兼容，修改字段语义必须升级包名或 Topic 版本。MQTT Topic 版本与 Protobuf 包版本需要同步规划，避免 dt/v1 携带语义已经变化的 v2 消息。

6. 配置设计

6.1 配置分层

配置分为四层：

层级 来源 示例
全局运行配置 本地 YAML、环境变量、命令行 运行模式、管理端口、日志级别
北向配置 本地 YAML 或部署系统注入 gRPC 地址、MQTT Broker、TLS、认证
Connector 配置 设备注册微服务推送、本地初始配置 协议、连接参数、轮询策略、默认标签
设备与数据点配置 设备注册微服务推送 地址、数据点映射、标签、上报策略覆盖

6.2 热加载流程

配置热加载按以下流程执行：

接到 DeviceConfigUpdate
  -> 校验 update_id、action、payload
  -> 解析为强类型配置对象
  -> 执行协议与字段级校验
  -> 生成配置差异
  -> 判断影响范围
  -> 应用变更
  -> 记录变更日志
  -> 返回 ConfigUpdateResponse

影响范围判断：

变更 处理方式
新增设备 添加到 Device Registry Cache，通知对应 Connector 增量加载
修改设备标签 更新缓存，后续消息使用新标签
修改数据点映射 通知 Connector/Converter 重载相关设备配置
删除设备 停止采集该设备，上报离线或移除状态
新增 Connector 实例化并启动新 Connector
修改 Connector 连接参数 尝试局部重载；如果协议连接必须重建，只影响该 Connector
删除 Connector 停止该 Connector，并标记其设备离线
修改全局上报策略 重建受影响策略状态
修改背压策略 即时更新 Backpressure Controller 配置

配置热加载失败时必须保持旧配置继续运行，并返回 ConfigUpdateResponse.success=false。对于同一个 update_id 的重复推送，应提供幂等处理，避免重复重载。

6.3 配置版本与乱序保护（FR-S-029a）

接口文档中 DeviceConfigUpdate 包含 update_id，用于操作级幂等（同一次推送重复到达时跳过）。但 update_id 不保证推送顺序，不同操作之间的先后关系无法仅凭 update_id 判断。

乱序保护机制： DeviceConfigUpdate 新增 entity_revision: int64（字段编号 5），由设备注册微服务为每个实体（device / connector）独立分配，每次变更 +1。数据传递微服务在本地为每个实体缓存已应用的 entity_revision，处理流程：

  1. 收到 DeviceConfigUpdate，检查 update_id 是否已处理过（幂等去重）；
  2. 已处理则忽略并返回 success；
  3. 未处理则比对 entity_revision：小于或等于本地已应用版本 → 过时变更，记录警告并忽略，返回 success；
  4. entity_revision 大于本地版本 → 应用变更，更新本地记录，记录变更日志。

跨服务注意：entity_revision 是对设备注册微服务的跨服务需求（CSC-002）。设备注册微服务须保证同一实体的 revision 严格单调递增。数据传递侧收到 revision 小于等于已应用版本的推送时将静默忽略（返回 success 但不应用）。

7. 接口对接设计

7.1 与数据处理与聚合微服务

上行 TELEMETRY、STATUS 和部分 EVENT 由数据处理与聚合微服务消费。该服务可通过 gRPC 订阅或 MQTT Topic 获取消息，并使用 DeviceIdentity.tags 做过滤与聚合。

需要对齐的问题：

问题 初步设计
tags 是否足够 当前保留 workshop、line、zone、system、floor、building 等建议键，也允许项目扩展
过滤能力 首版使用精确匹配 tag_match；正则、NOT 条件、范围条件留待确认
标签变更通知 首版让后续消息携带新标签；是否需要独立变更事件待确认

7.2 与智能命令编排与下发引擎微服务

命令编排引擎通过 SendCommand、SendCommandAsync 或 MQTT command Topic 发送下行指令。数据传递微服务负责校验、路由、转换、执行与回执。

需要对齐的问题：

问题 初步设计
ControlPayload.action 表达能力 首版使用字符串 action + params；复杂动作建议由设备配置中的 action mapping 解释
批量指令 接口文档当前为单条；若编排引擎需要批量下发，应新增批量接口或 batch payload
异步回执 首版通过 CMD_RESPONSE 上行交付；是否需要回调地址或专用回执流待确认
指令幂等 command_id 必须参与执行去重和日志追踪

7.3 与设备注册微服务

设备注册微服务负责设备台账、标签、Connector 配置和设备准入。数据传递微服务通过 PushDeviceConfig 或 MQTT config Topic 承接配置变更，并通过发现事件上报候选设备。

需要对齐的问题：

问题 初步设计
自动发现接入 数据传递侧只上报候选设备，等待设备注册侧确认
配置推送触发条件 由设备注册服务定义；数据传递侧只承接接口
批量配置 当前接口偏单条变更；首版开发应预留批量变更处理入口
版本与幂等 当前 update_id 可用于幂等，配置版本仍需跨服务确认

7.4 与本地策略与规则缓存微服务

该服务主要消费设备事件。数据传递微服务只提供 EVENT 交付，不进行策略判断。事件 payload 中的 event_type、severity、description 和 data 字段需与规则缓存服务进一步确认，尤其是事件类型命名、严重级别映射与是否需要工艺上下文。

8. 安全设计

方案A默认为同机通信，可在有要求时启用 mTLS。方案B必须启用 TLS，并支持 Token 或客户端证书认证。MQTT Client ID 使用 gateway-{gatewayId}，gatewayId 需要全局唯一。

第三层纯自定义插件需要隔离策略：

插件类型 隔离方式
可信、性能敏感插件 进程内注册，配合 panic 恢复、超时控制和权限边界
不可信、复杂或供应商交付插件 独立进程 sidecar，通过本地 gRPC 或 Unix domain socket 与主进程交互

插件不得直接访问核心状态、其他 Connector 数据、北向认证凭据和缓冲存储。sidecar 插件的接口应只暴露必要的上行消息、下行指令和状态查询能力。

9. 可观测性设计

管理接口统一提供：

端点 说明
/healthz 进程存活检查，只要主进程可响应即返回 200
/readyz 就绪检查，需要 Connector 初始化、北向通道状态满足运行模式要求
/metrics Prometheus 兼容指标

核心指标：

类别 指标
Connector 状态、设备数、错误数、平均延迟、重启次数
设备 在线数、离线数、最后通信时间
上行 原始采集速率、策略通过率、北向发送速率
下行 指令接纳数、执行成功率、超时率、重试次数
缓冲 pending 数量、completed 数量、容量使用率、续传进度
背压 队列使用率、触发次数、当前策略、解除耗时
系统 CPU、内存、goroutine 数、文件描述符数量

日志应采用 JSON 格式。转换失败、Connector 异常、配置热加载失败、缓冲容量告警、指令超时、背压触发等事件必须有明确错误码和关联 ID。

10. 可靠性与错误处理

错误处理遵循四个原则：

  1. 单条数据异常只影响该条数据；
  2. 单个 Connector 异常只影响其管理的设备；
  3. 北向断连时方案B进入缓冲模式，方案A进入背压或错误返回；
  4. 所有数据丢弃、指令失败、配置拒绝都必须可追踪。

错误码沿用接口文档中的 DT-{模块}-{序号} 结构（含 DT-CMD-005 command_id 重复拒绝）。开发时建议将错误码定义为统一枚举或常量，避免各模块手写字符串。

对于 MQTT QoS 1 产生的重复上行消息，上游消费者可通过 message_id 去重。对于 QoS 2 指令，微服务自身仍需记录 command_id，防止重复执行同一控制动作。

12. 开发阶段划分

12.1 P0：骨架与接口

P0 目标是让服务可启动、可加载配置、可暴露管理端口、可通过 gRPC 或 MQTT 完成最小消息流转。

交付内容：

模块 内容
Protobuf DeviceMessage、payload、配置更新、指标消息
Bootstrap 配置加载、环境变量覆盖、日志初始化
Runtime Supervisor、context 生命周期、模块启动停止
管理接口 /healthz、/readyz、/metrics
gRPC Adapter 方案A最小订阅与下行命令接口
MQTT Adapter 方案B最小发布、订阅、重连

12.2 P1：首个南向协议闭环

P1 目标是完成一个协议从采集到上报、从指令到回执的闭环。建议优先选择 Modbus TCP，因为寄存器映射、轮询、写寄存器和测试模拟较容易控制。

交付内容：

模块 内容
Modbus TCP Connector 轮询读取、状态检测、写寄存器或线圈
Converter Engine 上行解析、下行编码、表达式转换、标签合并
Command Router deviceId 路由、超时、重试、错误返回
Ack Tracker 指令状态追踪、同步与异步回执
单元测试 Converter、路由、配置校验

12.3 P2：方案B可靠传输

P2 目标是补齐分体式部署所需的缓冲、续传、限速和北向断连恢复。

交付内容：

模块 内容
Buffer Store SQLite pending/completed 两阶段确认
Replay Worker 历史数据按时间次序补发、限速、批量确认
MQTT QoS 按消息类型设置 QoS，处理重连和遗嘱消息
背压控制 队列水位、策略触发、指标暴露
集成测试 Broker 断连、恢复、重复消息、TTL 清理

12.4 P3：配置热加载与扩展协议

P3 目标是让设备注册微服务可以动态增删改设备和 Connector，并逐步扩展 MQTT Device、OPC-UA 等协议。

交付内容：

模块 内容
Config Manager DeviceConfigUpdate 校验、幂等、差异分析、entity_revision 乱序保护
Connector Reload 增量设备变更、Connector 局部重载
OPC-UA Connector Subscription、Read、Write、Call（与 MQTT Device 并行推进）
MQTT Device Connector 设备侧 JSON Topic 接入（与 OPC-UA 并行推进）
插件接口 进程内注册；sidecar 接口 proto 定义 + mock 实现（验证接口可行性）

以下内容来自需求、接口文档和跨服务协作备忘中的未定边界。它们不应阻塞基础开发，但会影响接口冻结和首版范围。

编号 问题 影响 处理结果 状态

16. 结论

首版开发应围绕“统一数据模型、可扩展 Connector、双向 Converter、北向双模式、配置热加载、方案B可靠续传”六条主线推进。ThingsBoard IoT Gateway 的 Connector、ReportStrategy、EventStorage 和远程配置思路可以作为架构参考，但本微服务应保持独立数据模型、独立接口和独立实现路线，尤其要强化工业控制场景需要的下行指令生命周期、回执追踪和跨服务配置边界。

从开发次序看，先完成 Go + Protobuf + gRPC/MQTT 的运行骨架，再用 Modbus TCP 做第一个端到端闭环，随后补齐方案B缓冲续传与配置热加载。跨服务未确认内容进入设计问题清单，在接口冻结前逐项确认；这样既能启动编码工作，也能避免把仍需讨论的外部依赖过早固化进实现。
