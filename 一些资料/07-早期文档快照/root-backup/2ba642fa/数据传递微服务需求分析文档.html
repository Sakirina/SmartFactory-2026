1. 概述

1.1 定位

数据传递微服务是智能工厂物联网平台中的边缘中间件组件，负责外围设备与边缘控制节点之间的双向数据传递。

它是什么：

  • 设备与边缘控制节点之间的通信中间层
  • 多协议适配器（南向接入各类工业设备）
  • 数据格式归一化引擎（将异构设备数据转为统一模型）
  • 双向数据通道（上行遥测 + 下行指令）

它不是什么：

  • 不是业务规则引擎（规则判断由"智能命令编排与下发引擎微服务"负责）
  • 不是边缘计算节点（不做本地数据分析、模型推理、阈值告警）
  • 不是数据持久化存储（仅做传输中的临时缓冲）
  • 不是安全联锁执行器（安全联锁由 PLC/SIS 系统直接处理，不经过本微服务）
  • 不是设备元数据管理者（设备台账、归属标签、设备准入的增删改查由「设备注册微服务」负责）
  • 不是"边缘控制节点 ↔ 云端"的通信模块（那是独立的数据传递模块，职责仅为边缘与云端间的收发）

1.2 核心职责

四个字概括：收、整、传、发。

职责 说明 数据方向
收 从外围设备采集遥测数据、设备状态、事件信息 设备 → 微服务
整 将不同协议/格式的原始数据归一化为统一数据模型 内部处理
传 将归一化后的数据上报给边缘控制节点内的上游微服务 微服务 → 上游
发 接收上游微服务下发的指令，转译为设备协议帧并下发 上游 → 微服务 → 设备

1.3 产品定位

本微服务是通用平台组件，不针对特定工厂或设备清单设计。需具备足够的协议扩展能力，适配不同客户场景下的设备接入需求。

1.4 内部数据管线概览

数据在微服务内部经过清晰的分层处理，各层职责独立：

上行路径：
  南向协议层 → Connector → Converter → [DeviceFilter] → [ReportStrategy] → 北向接口
     (收)         (收)        (整)         (整/传)           (传)            (传)

下行路径：
  北向接口 → CommandRouter → Connector → 反向Converter → 南向协议层
    (发)        (发)          (发)          (发)            (发)

方括号 [...] 表示可选组件——可启用也可跳过。

2. 部署架构

本微服务支持两种部署模式，适应不同的成本与规模场景。

2.1 方案A：嵌入式部署（省钱省心版）

┌─ 边缘控制节点（单台设备）───────────────────────────┐
│                                                 │
│  ┌────────────┐ ┌──────────────┐ ┌──────────┐   │
│  │数据处理与聚合 ││本地策略与规则缓 │ │命令编排与  │   │
│  │微服务       │ │存微服务       │ │下发引擎    │   │
│  └─────▲──────┘ └──────▲───────┘ └────┬─────┘   │
│        │               │              │         │
│  ┌─────┴───────────────┴──────────────▼──────┐  │
│  │           数据传递微服务                    │  │
│  └─────▲──────────────────────────────┬──────┘  │
└────────┼──────────────────────────────┼─────────┘
         │ 南向                          │ 南向
    ═════╧══════════════════════════════╧══════
              外围设备层

适用场景： 设备规模较小（单节点 < 数百台）、预算有限、网络拓扑简单。

北向通信特点： 进程间通信（gRPC over localhost 或 Unix domain socket），低延迟、高可靠。

2.2 方案B：分体式部署

┌─ 边缘控制节点 ─────────────────────────┐
│  ┌────────────┐ ┌────────┐ ┌───────┐ │
│  │数据处理与   │ │规则缓存 │ │命令编排  │ │
│  │聚合微服务   │ │微服务   │ │引擎    │ │
│  └─────▲──────┘ └──▲─────┘ └──┬────┘ │
│        │           │          │      │
│  ┌─────┴───────────┴──────────▼───┐  │
│  │      聚合/路由层（协议转译）       │  │
│  └─────▲──────────────────────────┘  │
└────────┼─────────────────────────────┘
         │ 北向（跨网络）
         │
┌────────┼──── 边缘网关设备 ─────────────┐
│  ┌─────┴──────────────────────────┐  │
│  │       数据传递微服务             │  │
│  └─────▲──────────────────┬───────┘  │
└────────┼──────────────────┼──────────┘
         │ 南向              │ 南向
    ═════╧══════════════════╧══════
              外围设备层

适用场景： 设备规模大或分布式部署、需要多个网关聚合、设备层与控制节点不在同一物理网络。

北向通信特点： 跨网络通信（MQTT over TCP/TLS），需考虑断线续传、消息可靠性、带宽优化。

2.3 部署模式对比

维度 方案A（嵌入式） 方案B（分体式）
部署拓扑 单设备，全部微服务共存 网关设备 + 控制节点分离
北向通信 gRPC（本地） MQTT（跨网络）
断线续传 不需要 需要（本地缓冲）
上报策略 通常无需（本地带宽充足） 建议启用（节省跨网络带宽）
水平扩展 微服务实例扩展 增加网关设备
适用规模 小到中型 中到大型
运维复杂度 低 中

3. 功能需求

3.1 南向采集（设备 → 微服务）

3.1.1 协议适配

FR-S-001 微服务须支持通过 Connector 组件接入不同通信协议的设备。

FR-S-002 协议适配采用三层策略：

层级 策略 覆盖率 说明
第一层 魔改主流协议 ~80% 基于 Modbus、OPC-UA、MQTT、BACnet、HTTP 等主流协议，允许字段级自定义扩展
第二层 字段拼装组合 ~15% 提供可视化/声明式的字段拼装能力，通过配置定义数据帧结构、字段偏移、编解码规则
第三层 纯自定义插件 ~5% 提供插件接口，允许开发人员用代码实现完全自定义的协议解析

FR-S-003 每个 Connector 实例须独立运行，单个 Connector 异常不得影响其他 Connector 的正常工作。Connector 须具有明确的生命周期状态：初始化中 → 运行中 → 异常 → 已停止。

3.1.2 通信对象

FR-S-004 微服务须支持与以下四类南向通信对象交互：

类型 特征 典型协议
直连传感器/执行器 微服务直接与设备通信 Modbus RTU/TCP, BACnet
PLC / RTU 设备数据先汇聚至 PLC，微服务与 PLC 通信 OPC-UA, Modbus TCP, S7
DTU / 协议网关 中间设备做协议转换，微服务接收转换后的数据 MQTT, HTTP, TCP 自定义
子网关 下级网关聚合一组设备数据后上报 MQTT, gRPC

3.1.3 设备接入

FR-S-005 微服务须同时支持两种设备接入方式：

  • 预配置接入： 设备注册微服务推送设备配置，数据传递微服务据此建立采集通道
  • 自动发现接入： 设备上线后通过协议层机制（如 mDNS、OPC-UA Discovery、MQTT 自注册）被数据传递微服务识别

FR-S-006 自动发现的设备，数据传递微服务不得自行纳入正式采集。须将发现信息上报至设备注册微服务，待其确认并下发正式配置后，方可开始数据采集。

3.1.4 数据归一化

FR-S-007 所有协议采集的原始数据须经过 Converter 组件转换为统一的 DeviceMessage 数据模型（详见第5章）。

FR-S-008 Converter 须支持以下转换能力：

  • 字段映射（原始字段名 → 标准字段名）
  • 值变换（线性缩放、单位转换、枚举映射、表达式运算）
  • 数据质量标注（GOOD / BAD / UNCERTAIN）
  • 时间戳校正（设备时间 vs 采集时间，应标注时间来源）

FR-S-008a 设备归属标签（tags）由外部的「设备注册微服务」管理并下发。数据传递微服务在生成 DeviceMessage 时须将这些标签填入 DeviceIdentity.tags 字段，随每条消息透传至上游消费者。微服务本身不解释标签含义——标签的语义由上游服务自行定义和使用。

FR-S-008b 标签须支持 Connector 级默认值继承：Connector 配置中设置的归属标签自动应用于其下所有设备，设备级标签可覆盖 Connector 级默认值。合并优先级：设备级 > Connector 级。

3.2 南向下发（微服务 → 设备）

3.2.1 指令转译

FR-S-009 微服务须将上游下发的标准格式指令，通过反向 Converter 转译为目标设备的协议帧格式。

FR-S-010 反向 Converter 须与上行 Converter 共用同一份设备配置，保证同一设备的上行和下行映射一致。

设计说明：与 ThingsBoard Gateway 的 Converter 仅处理上行不同，本微服务要求 Converter 天然双向——同一配置同时定义上行解析和下行编码。这是本微服务区别于 TB Gateway 的核心设计选择之一。

3.2.2 指令类型

FR-S-011 微服务须支持以下三类下行指令：

类型 说明 时延要求 示例
参数更新（PARAM_UPDATE） 更新设备运行参数或配置 秒级 修改采集频率、调整阈值
控制指令（CONTROL） 触发设备执行特定动作 百毫秒级 启停电机、开关阀门
数据查询（QUERY） 主动读取设备当前值 秒级 读取当前温度、查询设备状态

3.2.3 回执与重试

FR-S-012 每条下发指令须具有唯一标识（commandId），微服务须追踪指令的执行状态。

FR-S-013 指令执行状态生命周期：

PENDING → SENT → DELIVERED → EXECUTED / FAILED / TIMEOUT

FR-S-014 微服务须支持可配置的超时时间和重试策略：

  • 超时时间：按指令类型可配置（CONTROL 指令默认较短）
  • 重试次数：可配置，默认 3 次
  • 重试间隔：支持固定间隔和指数退避

FR-S-015 最终执行结果（成功/失败/超时）须作为 CMD_RESPONSE 类型消息上报给上游。

设计说明：TB Gateway 的下行仅支持 RPC 和属性更新两种模式，回执依赖平台侧 RPC 超时机制。本微服务的下行管道显著更丰富——三种指令类型、完整的生命周期追踪、微服务内建重试——这是针对工业控制场景的核心增强。

3.3 北向上报（微服务 → 上游服务）

FR-S-016 微服务须将以下四类消息上报给上游微服务：

消息类型 目标消费者 说明
TELEMETRY（遥测数据） 数据处理与聚合微服务 设备周期性采集的测量值
STATUS（设备状态） 数据处理与聚合微服务 设备上线/离线/故障状态变更
EVENT（设备事件） 数据处理与聚合微服务、本地策略与规则缓存微服务 设备主动上报的事件（报警、阈值触发等）
CMD_RESPONSE（指令回执） 智能命令编排与下发引擎微服务 下发指令的执行结果

FR-S-017 上报须支持批量模式，允许将多条消息打包发送以提高吞吐效率。

FR-S-018 方案A和方案B对上游暴露不同的接口实现（详见接口文档），但数据模型保持一致。

3.4 北向接收（上游服务 → 微服务）

FR-S-019 微服务须接收来自"智能命令编排与下发引擎微服务"的下行指令，并路由到正确的 Connector 执行下发。

FR-S-020 指令路由须基于 deviceId 定位目标设备所属的 Connector 实例。

FR-S-021 当目标设备不在线或目标 Connector 不可用时，微服务须立即返回错误状态，不做静默丢弃。

3.5 本地缓冲与断线续传

以下需求仅适用于方案B（分体式部署）。方案A 下北向通信为本地调用，无需缓冲。

FR-S-022 当北向网络中断时，微服务须将采集到的数据缓存至本地存储。

FR-S-023 本地缓冲须支持以下策略：

配置项 说明 默认值建议
最大缓冲容量 超出后按 FIFO 策略淘汰旧数据 可配置（磁盘容量相关）
数据 TTL 超过存活时间的数据自动清理 7 天
续传顺序 网络恢复后按时间顺序补发 先旧后新
续传速率 避免网络恢复后的流量洪峰 可配置限速

FR-S-024 网络恢复后，微服务须自动进入续传模式，将缓存数据按序补发，同时不影响实时数据的正常上报。

FR-S-024a 缓冲存储须采用两阶段提交模式，确保数据不在"写入缓冲"和"确认发送"之间丢失：先写入本地存储，发送成功后再标记为已完成，最后批量清理已完成记录。

FR-S-025 断连期间收到的下行指令须返回明确的错误状态（"设备不可达"），不做本地缓存排队。

3.6 上报策略（可选带宽优化）

本节定义的上报策略为可选能力，默认关闭（即所有数据即采即传）。启用后可有效降低北向带宽消耗，尤其适用于方案B跨网络场景。

FR-S-033 微服务须支持可配置的上报策略，控制归一化后的数据在进入北向上报通道之前的过滤行为。

FR-S-034 上报策略须支持以下模式：

模式 行为 适用场景
ON_RECEIVED（默认） 数据到达即上报 实时性要求高的场景
ON_CHANGE 仅当数据值发生变化时上报 状态位、开关量等变化频率低的数据
ON_REPORT_PERIOD 按固定周期上报最新值 需要降频的高采集频率设备
ON_CHANGE_OR_REPORT_PERIOD 变化时立即上报，无变化时按周期兜底 平衡实时性与带宽的通用场景

FR-S-035 上报策略须支持多级配置，低级别配置覆盖高级别：

  • 全局默认策略（所有 Connector 的兜底配置）
  • Connector 级策略（覆盖该 Connector 下所有设备的默认策略）
  • 数据点级策略（精确控制到单个 key 的上报行为）

FR-S-036 上报策略仅对 TELEMETRY 类型消息生效。STATUS、EVENT、CMD_RESPONSE 类型消息不受上报策略影响，始终即时上报。

3.7 背压控制

FR-S-037 当上行数据产生速率超过北向通道消费速率时，微服务须具备背压控制机制，避免内存无限增长。

FR-S-038 背压控制须支持可配置的策略：

策略 行为 适用场景
阻塞采集 暂停 Connector 的数据采集，待队列恢复后继续 不允许丢数据的场景
丢弃最旧 淘汰队列中最早的数据，腾出空间给新数据 关注最新数据的场景
降级采样 临时降低采集频率，减少数据产生速率 带宽受限的过渡场景

FR-S-039 背压触发和解除须通过监控指标对外可见（见 3.9），不得静默发生。

3.8 配置管理

FR-S-026 以下配置变更须支持热加载，不中断服务运行：

  • 新增/删除/修改设备
  • 修改设备的采集参数（采集频率、字段映射等）
  • 新增/修改 Connector 实例配置
  • 调整上报策略（批量大小、发送间隔等）

FR-S-027 新增协议插件（第三层纯自定义）允许短暂的 Connector 重载，但不得影响其他 Connector 的运行。

FR-S-028 配置来源须支持：

  • 本地配置文件——用于初始部署和离线场景
  • 远程配置下发（由「设备注册微服务」推送）——运行时的设备增删改查、标签变更均通过此通道下发

FR-S-029 配置变更须记录变更日志，包含变更时间、变更内容、变更来源。

3.9 监控与可观测性

FR-S-030 微服务须暴露以下运行指标，供外部监控系统采集：

指标类别 具体指标
设备连接 当前在线设备数、各 Connector 连接设备数、设备上下线事件频率
数据吞吐 上行消息速率（条/秒）、下行指令速率、数据量（字节/秒）
协议通道 各 Connector 状态（运行中/异常/已停止）、各协议通道延迟
指令执行 指令成功率、平均响应时间、超时率、重试率
缓冲状态 当前缓冲消息数、缓冲容量使用率、续传进度（方案B）
背压状态 内部队列使用率、背压触发/解除事件、当前背压策略状态
上报策略 被策略过滤的消息数、实际上报率 vs 原始采集率（启用策略时）
系统资源 CPU 使用率、内存使用率、并发任务数

FR-S-031 指标须以结构化格式暴露，支持外部采集系统拉取。

FR-S-032 微服务须输出结构化日志，包含时间戳、级别、模块来源、关联的 deviceId/connectorId。

4. 非功能需求

4.1 弹性与可扩展性

NFR-001 微服务须设计为可水平扩展，单实例支撑的设备规模不设硬性上限。

NFR-002 性能基线参考（单实例，普通工控机硬件）：

指标 基线目标
支撑设备数 >= 500 台
上行吞吐量 >= 5,000 条消息/秒
下行指令延迟 <= 200ms（从收到指令到发出协议帧）
内存占用 <= 256MB（500 设备场景）
启动时间 <= 10 秒（含 Connector 初始化）

注：以上为设计参考基线，非硬性承诺。实际性能取决于设备类型、协议复杂度和硬件配置。

NFR-003 当实例负载接近上限时，须通过监控指标给出预警信号，而非静默降级。

4.2 信创合规

NFR-004 微服务须具备信创环境适配能力：

  • 支持在国产操作系统上运行（麒麟、统信 UOS）
  • 支持国产 CPU 架构编译（龙芯 LoongArch、飞腾 ARM、海光 x86）
  • 本地缓冲存储如使用嵌入式数据库，须预留国产数据库替换接口
  • 加密通信如涉及 TLS，须预留国密算法（SM2/SM3/SM4）适配接口

NFR-005 信创合规不作为 v1.0 的硬性交付要求，但架构设计须确保可替换性，避免对特定非国产组件的硬依赖。

4.3 安全性

NFR-006 方案B 下，北向通信须支持 TLS 加密传输。

NFR-007 方案B 下，微服务与边缘控制节点之间须有身份认证机制（如 Token、证书双向认证）。

NFR-008 Connector 插件（第三层纯自定义）须运行在受限环境中，不得直接访问微服务核心状态或其他 Connector 的数据。

4.4 可靠性

NFR-009 微服务异常退出后须支持自动重启，重启后自动恢复所有 Connector 连接。

NFR-010 单条异常数据（格式错误、转换失败）不得导致整个数据管道阻塞，须记录错误并跳过。

NFR-011 方案B 下，本地缓冲数据须持久化存储，微服务重启后缓冲数据不丢失。

4.5 可部署性

NFR-012 微服务须能以单一可执行文件形式部署，减少对运行环境的依赖（不依赖特定语言运行时、不依赖大量外部动态库）。

NFR-013 微服务须支持通过环境变量和命令行参数覆盖配置文件中的关键设置（如北向地址、日志级别），便于容器化和自动化部署。

5. 数据模型定义

5.1 统一信封：DeviceMessage

所有上行和下行数据均使用统一的信封格式，通过 direction 和 type 字段区分方向和用途。

DeviceMessage
├── messageId: string          // 全局唯一标识（UUID v7，含时间序信息）
├── timestamp: int64           // 消息产生时间（Unix 毫秒时间戳）
├── direction: enum            // UPSTREAM | DOWNSTREAM
├── source: DeviceIdentity     // 消息来源/目标设备
├── type: enum                 // 消息类型（见 5.2）
├── payload: bytes             // 具体内容（按 type 解析，见 5.3）
└── metadata: map<string,string>  // 可扩展的附加元数据

对标说明：TB Gateway 使用 ConvertedData（含 deviceName, deviceType, telemetry, attributes, metadata）作为统一格式。本微服务的 DeviceMessage 在以下方面不同：(1) 信封天然包含方向（UPSTREAM/DOWNSTREAM），上下行共用一个模型；(2) payload 是强类型 oneof 而非松散的 JSON 键值对；(3) 携带 tags 和 quality 等工业场景必要字段。

5.2 消息类型

direction type 说明
UPSTREAM TELEMETRY 设备遥测数据（周期性采集的测量值）
UPSTREAM STATUS 设备状态变更（上线/离线/故障）
UPSTREAM EVENT 设备事件（报警、阈值触发等）
UPSTREAM CMD_RESPONSE 下发指令的执行回执
DOWNSTREAM PARAM_UPDATE 参数/配置更新
DOWNSTREAM CONTROL 控制指令
DOWNSTREAM QUERY 数据查询请求

5.3 各类型 Payload 结构

TelemetryPayload（遥测数据）

TelemetryPayload
├── datapoints: []Datapoint
│   ├── key: string            // 数据点名称（如 "temperature"）
│   ├── value: oneof           // 值（number / string / bool / bytes）
│   ├── timestamp: int64       // 数据点级时间戳（可选，覆盖信封时间戳）
│   ├── quality: enum          // GOOD | BAD | UNCERTAIN
│   └── unit: string           // 单位（可选，如 "℃", "RPM"）

StatusPayload（设备状态）

StatusPayload
├── state: enum                // ONLINE | OFFLINE | ERROR | UNKNOWN
├── reason: string             // 状态变更原因（可选）
└── lastSeen: int64            // 最后一次成功通信的时间戳

EventPayload（设备事件）

EventPayload
├── eventType: string          // 事件类型标识
├── severity: enum             // INFO | WARNING | ALARM | CRITICAL
├── description: string        // 人类可读描述
└── data: map<string, string>  // 事件关联数据

CommandResponsePayload（指令回执）

CommandResponsePayload
├── commandId: string          // 对应的下发指令 ID
├── status: enum               // SUCCESS | FAILURE | TIMEOUT | REJECTED
├── message: string            // 结果描述（尤其在失败时）
└── result: map<string, string>  // 执行结果数据（可选，如查询返回值）

ParamUpdatePayload（参数更新）

ParamUpdatePayload
├── params: []ParamEntry
│   ├── key: string            // 参数名
│   ├── value: oneof           // 目标值
│   └── applyMode: enum        // IMMEDIATE | ON_RESTART

ControlPayload（控制指令）

ControlPayload
├── action: string             // 动作标识（如 "start", "stop", "set_speed"）
├── params: map<string, string>  // 动作参数
└── options: CommandOptions
    ├── timeout: int32         // 超时时间（毫秒）
    ├── retryCount: int32      // 最大重试次数
    └── priority: enum         // NORMAL | HIGH | URGENT

QueryPayload（数据查询）

QueryPayload
├── queryType: enum            // READ_CURRENT | READ_RANGE | READ_CONFIG
├── keys: []string             // 要查询的数据点名称列表
└── options: CommandOptions

5.4 DeviceIdentity（设备标识）

DeviceIdentity
├── deviceId: string              // 设备唯一标识（系统分配）
├── deviceName: string            // 人类可读名称
├── deviceType: string            // 设备类型分类
├── connectorId: string           // 所属 Connector 实例标识
├── protocol: string              // 通信协议类型标识
└── tags: map<string, string>     // 设备归属标签（车间/产线/区域/子系统等）

tags 使用约定：

tags 承载设备的归属维度信息，由设备配置阶段写入，数据传递微服务在每条消息中原样透传，不做解释或处理。上游消费者可据此进行过滤、路由、聚合。

推荐标签键（约定优于强制）：

键名 含义 示例
workshop 车间 "车间A"
line 产线 "产线3"
zone 区域 "注塑区"
system 所属子系统 "温控系统"
floor 楼层 "2F"
building 建筑 "东厂房"

允许项目按需扩展自定义键，不做 key 白名单限制。

7. 设计参考：ThingsBoard IoT Gateway 对标分析

本章记录对 ThingsBoard IoT Gateway（开源版本）的架构分析结果，说明本微服务从中吸收了哪些设计思路，以及在哪些方面做了不同的选择。

7.1 TB IoT Gateway 架构概要

TB IoT Gateway 的内部分为五层：

层级 职责 核心组件
入口与配置层 进程启动、配置文件加载、日志初始化 tb_gateway.json, logs.json
连接器层 协议适配，15 种内置连接器 Connector 接口、Converter
统一数据层 数据归一化为 ConvertedData ConvertedData, DeviceFilter, ReportStrategy
本地缓冲与发送层 事件队列、本地存储、可靠发送 EventStorage（内存/文件/SQLite）, 发送线程
平台管理与下行层 MQTT 平台连接、RPC 路由、远程配置 TBClient, RemoteConfigurator

全局由 TBGatewayService 作为中央编排器协调所有层的生命周期。

7.2 借鉴与决策矩阵

TB 概念 本微服务等价物 决策 理由
Connector 接口 Connector 接口 采纳 协议隔离是通用范式，接口签名根据双向需求重新设计
Converter（仅上行） Converter（双向） 增强 TB Converter 仅做上行转换，本微服务要求双向——同一配置定义上行解析和下行编码
ConvertedData DeviceMessage 重新设计 增加方向、强类型 payload、tags、quality 等工业场景字段
ReportStrategy（5 模式） 上报策略（4 模式，可选） 适配 去掉 DISABLED（无意义），增加多级配置（全局/Connector/数据点），标记为可选功能
DeviceFilter 由设备注册微服务管控 外移 设备准入是元数据管理职责，不在数据传递层自行决策
EventStorage（3 实现） 本地缓冲存储 采纳思路 采纳两阶段提交可靠性模式，但仅限方案B，实现方案由架构师决定
TBGatewayService 编排 微服务主流程 采纳思路 中央编排器模式清晰，但不照搬其"全局状态集中"的做法，倾向模块间通过通道解耦
远程配置（RemoteConfigurator） 由设备注册微服务推送配置 适配 TB 的远程配置直连平台，本微服务的配置来源是设备注册微服务（更清晰的职责边界）
gRPC 外部 Connector 路径 第三层纯自定义插件隔离机制 采纳思路 用于插件进程隔离，但本微服务不限于 gRPC——可选 gRPC sidecar 或其他隔离机制
15 种内置 Connector 三层协议策略 不同路线 不做"每协议一个内置类"的穷举，改用魔改主流+字段拼装+纯自定义的渐进策略
单向管道（上行为主） 双向对称管道 核心差异 TB 的下行仅有 RPC + 属性更新，本微服务的下行是完整管道（三种指令 + 生命周期追踪 + 重试）
Python 实现 计划使用编译型语言 不同路线 见附录C技术选型分析

C.1 实现语言

建议：Go

评估维度 Go Python（TB 现状） Rust
部署形态 单一静态二进制，零依赖 需 Python 运行时 + C 扩展库 单一二进制
信创交叉编译 GOOS/GOARCH 原生支持龙芯/飞腾 需要在目标平台逐一编译 C 扩展 支持但工具链成熟度较低
并发模型 goroutine + channel，轻量级万级并发 asyncio 或多线程（GIL 限制） async + tokio，性能最优但学习曲线陡
协议库生态 Modbus/OPC-UA/MQTT/BACnet 均有成熟库 成熟（TB 已验证） 部分协议库不成熟
团队上手成本 中等（语法简单，生态丰富） 低 高
内存占用 中（适合边缘设备） 高 低

核心理由：数据传递微服务 ~90% 工作负载是 I/O（串口/TCP/MQTT/gRPC），~10% 是数据转换。性能瓶颈不在 CPU 密集计算，而在并发连接管理和部署便捷性。Go 的 goroutine 原生适合此场景，单二进制部署解决信创环境的交叉编译痛点。

C.2 序列化与传输

组件 建议 理由
数据序列化 Protocol Buffers v3 强类型、向前/向后兼容、二进制编码体积小
方案A 北向传输 gRPC over HTTP/2 原生流式、双向通信、服务发现友好
方案B 北向传输 MQTT v5.0 跨网络可靠传输、QoS 保证、遗嘱消息支持断线检测
配置文件格式 YAML 人类可读、注释友好，适合工程师手工编辑

C.3 Converter 表达式引擎

数据点的值变换（线性缩放、单位转换、条件映射）建议使用轻量级表达式引擎，而非硬编码或完整脚本语言：

方案 特点 适用场景
声明式表达式引擎 安全沙箱、亚毫秒执行、无副作用 第一层（魔改主流协议）和第二层（字段拼装）的值变换
完整脚本语言（Lua/JS） 灵活但有安全和性能风险 不推荐用于常规转换

表达式引擎应支持：算术运算、比较、条件分支、字符串操作、位运算（工业协议常用）。

C.4 本地缓冲存储（方案B）

方案 特点 建议
嵌入式关系数据库（如 SQLite） 成熟、ACID、支持查询、跨平台 优先推荐——与 TB 的 EventStorage SQLite 实现类似思路，但完全独立实现
嵌入式 KV 存储 写入性能高、API 简单 适合对查询需求低的场景
文件存储 最简单、无依赖 可作为降级方案

C.5 协议库参考

以下为各主流协议的库选型方向（非指定）：

协议 方向 注意事项
Modbus TCP/RTU 主动轮询（Master） 需支持 RTU over TCP、自定义功能码
OPC-UA 客户端（Subscription + Read/Write/Call） 需支持安全策略（Basic256Sha256）、证书
MQTT 客户端（Subscribe + Publish） 需支持 v5.0 特性（User Properties、Shared Subscription）
BACnet/IP 客户端（ReadProperty/WriteProperty/COV） 生态较小，可能需要封装 C 库
HTTP/REST 客户端（轮询）或服务端（webhook） 相对简单

C.6 插件隔离策略

针对第三层纯自定义插件的隔离：

隔离级别 机制 适用场景
进程内隔离 独立执行单元 + panic 恢复 可信插件，性能优先
进程间隔离（gRPC sidecar） 插件独立进程，通过本地 gRPC 通信 不可信或不稳定插件，安全优先

建议默认使用进程内隔离，为高风险插件提供可选的进程间隔离路径。此思路参考了 TB Gateway 的可选 gRPC 外部连接器路径（TBGRPCServerManager），但协议和接口完全独立设计。
