# 跨服务协作备忘

> **用途：** 记录各微服务需求讨论中产生的跨服务依赖、待对齐接口、遗留问题。每个微服务在独立会话中讨论，本文件是会话之间传递"包袱"的唯一通道。  
> **使用方式：**  
> 1. 当某个微服务的需求讨论中发现涉及其他微服务的问题，在此文件中登记一条条目  
> 2. 讨论另一个微服务时，先检查本文件中与该微服务相关的待办项  
> 3. 问题解决后更新状态为 `已解决`，注明解决方式和所在文档位置  
> **格式约定：** 每条条目包含来源、目标、状态、描述、解决建议  
> **最后更新：** 2026-06-07

### CSC-002 设备注册微服务需定义「设备配置推送」的触发机制与数据格式对齐

| 字段 | 内容 |
|------|------|
| **来源** | 数据传递微服务需求讨论 |
| **目标微服务** | 设备注册微服务 |
| **状态** | `待讨论` |
| **描述** | 数据传递微服务已定义了接收配置推送的接口（方案A: `PushDeviceConfig` gRPC Method; 方案B: `dt/v1/down/{gatewayId}/config` MQTT Topic），包含 `DeviceConfigUpdate` 消息结构（支持设备/Connector 的增删改）。设备注册微服务作为调用方，需确认此接口是否满足其推送需求，或提出调整要求。 |
| **需要设备注册微服务确认的内容** | 1. `DeviceConfigUpdate` 的 `UpdateAction` 枚举是否覆盖所有操作场景（v2.0 新增 `UPDATE_GLOBAL`） 2. `DeviceConfigPayload` 和 `ConnectorConfigPayload` 的字段是否充分（v2.0 新增上报策略配置字段） 3. 批量推送需求（如一次性推送整个 Connector 下所有设备）是否需要额外接口 4. 配置版本号/乐观锁机制是否需要 |
| **相关文档** | `数据传递微服务接口文档.md` v2.0 3.1.1 (`PushDeviceConfig`), 3.1.2 (`DeviceConfigUpdate` 消息定义, 含 `GlobalConfigPayload`), 3.2.2 (MQTT config Topic) |

### CSC-003 命令编排引擎需对齐下行指令的 Protobuf 消息格式

| 字段 | 内容 |
|------|------|
| **来源** | 数据传递微服务需求讨论 |
| **目标微服务** | 智能命令编排与下发引擎微服务 |
| **状态** | `待讨论` |
| **描述** | 数据传递微服务已定义了下行指令的统一格式：`DeviceMessage` 信封 + `ControlPayload` / `ParamUpdatePayload` / `QueryPayload` 三种 Payload。命令编排引擎作为指令的发起方，需确认此格式能否满足其编排输出的表达需求。 |
| **需要命令编排引擎确认的内容** | 1. `ControlPayload.action` 的字符串标识方式是否足够灵活 2. `CommandOptions`（timeout, retry, priority）是否覆盖了编排引擎需要控制的全部参数 3. 异步指令模式下，回执通过 `CMD_RESPONSE` 上行消息返回，编排引擎是否需要额外的回调机制 4. 指令是否需要支持批量下发（当前接口为单条） |
| **相关文档** | `数据传递微服务接口文档.md` 2.3 (Payload 定义), 3.1.1 (`SendCommand`, `SendCommandAsync`), 3.2.2 (MQTT command Topic) |

### CSC-004 数据处理与聚合微服务需确认 tags 过滤与聚合需求

| 字段 | 内容 |
|------|------|
| **来源** | 数据传递微服务需求讨论（团队反馈触发） |
| **目标微服务** | 数据处理与聚合微服务 |
| **状态** | `待讨论` |
| **描述** | 数据传递微服务已在 `DeviceIdentity` 中新增 `tags` 字段（如 workshop, line, zone, system），每条消息都携带设备归属标签。数据处理与聚合微服务作为主要消费者，需确认推荐的标签键是否满足其分组聚合需求。 |
| **需要数据处理微服务确认的内容** | 1. 当前推荐的标签键（workshop, line, zone, system, floor, building）是否满足聚合维度需求 2. 是否需要在 `SubscribeRequest.tag_match` 之外增加更复杂的过滤能力（如正则匹配、NOT 条件） 3. 标签变更时（如设备从产线3移到产线5），是否需要变更通知，还是依赖下一条消息自动携带新标签即可 |
| **相关文档** | `数据传递微服务需求分析文档.md` 5.4 (tags 约定), FR-S-008a/008b; `数据传递微服务接口文档.md` 2.2 (DeviceIdentity.tags), 3.1.2 (SubscribeRequest.tag_match) |
