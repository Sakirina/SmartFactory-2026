ThingsBoard
四大核心组件
架构拆解

拆解对象：Edge、IoT Gateway、TBMQ、Trendz Analytics。Server / Cloud 不在范围内，但它是这四个组件的协调中枢——设备建模、租户隔离、规则执行、数据可视化都绕不开它。

Edge边缘本地处理与云端同步
IoT Gateway工业协议与平台数据模型转换
TBMQ大规模 MQTT 消息骨干
Trendz面向 IoT 数据的分析与预测层

Data Flow

端到端数据流

这四个组件不互相替代，各管一段：Gateway 管协议适配，Edge 管断网自治，TBMQ 管大规模消息吞吐，Trendz 管数据分析。下面是一条数据从设备到分析的完整链路。

1

现场接入

设备直连 Edge / Server，或经 Gateway 接入。Gateway 搞定 Modbus、OPC-UA、BACnet、CAN、BLE、SNMP、OCPP 这些工业协议。

2

数据转换

Connector 拉取或订阅原始数据，Converter 转成平台认识的 telemetry、attributes、RPC response。

3

边缘处理

Edge Transport 收 MQTT / HTTP / CoAP / LwM2M / SNMP，Rule Engine 在本地跑过滤、富化、存盘、告警。

4

云端同步

Cloud Manager 把要上云的事件攒进队列，走双向 gRPC 流推给 Server / Cloud。

5

MQTT 骨干

TBMQ 给设备和应用客户端当 MQTT broker。Kafka 存消息、会话、订阅，Redis / Valkey 管持久消息投递。

6

分析闭环

Trendz 走内部 API 拉实体和遥测数据，输出分析视图、预测模型、异常检测。

Products

四个主体

按产品定位、源码模块、运行时组件三层拆。Trendz 源码不公开，靠官方文档和配置参考补齐。

ThingsBoard Edge

Edge

装在现场的 ThingsBoard 实例。本地处理数据、存状态，选择性地往云端同步。

Transport收 MQTT / HTTP / CoAP / LwM2M / SNMP，校验凭据后丢给 Rule Engine。
Rule Engine本地跑规则链：过滤、富化、存盘、告警、RPC、push to cloud。
Cloud Manager读 cloud event queue，gRPC 上推事件，下拉配置和实体变更。
Local StatePostgreSQL 存实体、遥测、告警、cloud_events。高吞吐场景可换 Kafka 队列。

ThingsBoard IoT Gateway

Gateway

Python 写的协议桥。老设备不会说 ThingsBoard 的话，Gateway 给它们当翻译。

Gateway Service拉起连接器、初始化存储、连 ThingsBoard Client，上报运行统计。
ConnectorsMQTT、Modbus、OPC-UA、BACnet、BLE、CAN、FTP、KNX、ODBC、OCPP、SNMP，每种协议一个目录。
ConvertersUplink 把协议数据转成平台模型，Downlink 反过来。
Event Storage文档写了 memory 和 file 两种，源码里还有个 SQLite 实现，重启不丢数据。

ThingsBoard MQTT Broker (TBMQ)

Broker

独立的 MQTT broker，冲着百万级连接、持久会话、共享订阅去的。

Listener LayerNetty 起 TCP / TLS / WebSocket / WSS，标准 channel pipeline。
Session & Actor每个客户端一个 Actor，管会话状态、QoS in-flight、topic alias。
Kafka Backbone按 msg.all、msg.persisted、msg.app.$CLIENT_ID、retained、session、subscription 分主题。
Integration Executor每个 integration 独立 Kafka 主题，消费后转发到 HTTP / MQTT / Kafka 外部端点。

Trendz Analytics

Analytics

分析插件，吃平台已有的设备、资产、时序数据，产出分析视图、预测和异常检测。

ThingsBoard LinkTrendz 和 ThingsBoard 各配一个内部 URL 互指，配好就自动 discovery。
Topology Discovery拉取实体、关系、字段，按资产层级和设备类型组织分析维度。
Analytics WorkspaceMetric Explorer、View Builder、calculated fields、forecast views、anomaly models。
Runtime ServicesTrendz PostgreSQL、Caffeine / Redis cache、Python Executor WebSocket、Task Service。

Deployment

部署理解

四个组件的典型搭配方式，偏工程落地视角。

场景 推荐组合 理由
单现场、弱网络 Gateway + Edge + Server / Cloud Gateway 负责老设备接入，Edge 在现场保存和处理数据，网络恢复后再同步云端。
海量 MQTT 设备 TBMQ + Server / Cloud + Trendz TBMQ 承担 MQTT 会话、QoS、共享订阅和吞吐，平台侧处理实体与规则，Trendz 做后续分析。
工业协议 + 边缘自治 Gateway + Edge 现场设备不用改固件，规则、告警、仪表盘和 RPC 可以在本地继续运行。
预测维护和运营分析 Server / Cloud + Trendz，可接入 Edge 或 TBMQ 数据 Trendz 的拓扑发现、计算字段、预测和异常检测依赖平台已经采集的实体关系与遥测。
