IoT Gateway 架构深潜

从源码实际组织结构出发，拆解运行时线程模型、数据管道、每个模块的内部机制和配置映射。所有结论来自 thingsboard-gateway 源码。

Data Pipeline

数据管道：从设备到平台的完整链路

一条数据从 Modbus 寄存器到 ThingsBoard 平台的完整旅程，经过 7 个阶段。每个阶段都有明确的输入输出边界。

1 · 协议采集
Connector.open()
  • 每种协议一个 Connector 实例，独立线程运行
  • Modbus：asyncio 事件循环，pymodbus 读寄存器
  • OPC-UA：节点订阅回调
  • MQTT：桥接订阅第三方 broker
→
2 · 数据转换
Converter.convert()
  • Uplink：原始字节/寄存器值 → ConvertedData
  • 绑定 deviceName + deviceType
  • 拆分 telemetry（带 ts）和 attributes（无 ts）
  • 每个数据点绑定 DatapointKey + ReportStrategy
→
3 · 设备过滤
DeviceFilter.validate_device()
  • connector 维度的 allow/deny 列表
  • 正则匹配 deviceName
  • 被拒绝的设备返回 FORBIDDEN_DEVICE
  • 通过的数据进入下一阶段
→
4 · 上报策略
ReportStrategyService.filter_data_and_send()
  • 逐数据点检查 ReportStrategy 配置
  • ON_CHANGE：缓存旧值，比较后决定
  • ON_REPORT_PERIOD：定时器触发批量发送
  • 通过的数据 put 进 converted_data_queue
→
5 · 本地存储
EventStorage.put()
  • Storage fill thread 从队列消费
  • 按 maxPayloadSizeBytes 拆大包
  • JSON 序列化后写入 Memory/File/SQLite
  • 断网时数据安全积压在此
→
6 · 批量发送
__read_data_from_storage()
  • Send data thread 循环读取 event_pack
  • 按 deviceName 聚合 telemetry + attributes
  • 等 MQTT 连接可用才发
  • 发送后调 event_pack_processing_done()
→
7 · MQTT 上行
TBClient → ThingsBoard
  • TBGatewayMqttClient 发布
  • QoS 1 保证至少一次投递
  • 等待 PUBACK 确认
  • 失败时数据留在 storage 重发
对你项目的启发：管道的核心设计是「宽进严出」——前端尽量多收数据，中间层层过滤和策略判断，最后只把有价值的数据发出去。你的边缘控制节点可以照搬这个模式，但需要在第 3 步之后插入「指令安全研判」和「数据质量治理」两个阶段。
Runtime

运行时线程模型

Gateway 是一个多线程 Python 进程。TBGatewayService.__init__ 在启动时拉起以下守护线程，每个线程有明确职责。

每协议一个

Connector 线程

每个 Connector 实例在独立线程/asyncio 事件循环中运行。Modbus connector 用 asyncio.run() 起自己的事件循环，独立于主线程。崩溃不影响其他 connector。

核心线程

Storage Fill Thread

消费 converted_data_queue，批量处理（每批最多 1000 条或 500ms），按 maxPayloadSize 拆包后写入 EventStorage。名字叫 "Storage fill thread"。

核心线程

Send Data Thread

循环调 event_storage.get_event_pack()，按 deviceName 聚合数据，通过 MQTT 发送到平台。发送成功后调 event_pack_processing_done() 确认。

守护线程

RPC Processing Thread

处理 RPC reply 队列。网关执行完 RPC 后，回复通过这个线程发回平台，避免阻塞主数据管道。

守护线程

RPC to Devices Thread

接收平台下发的 RPC 请求，路由到对应 Connector 的 server_side_rpc_handler()。有超时机制，超时未响应的 RPC 自动取消。

守护线程

Attributes Sync Thread

新连接建立后，遍历所有已知设备，主动向平台请求最新 shared attributes。确保设备状态和平台同步。

守护线程

Device Idle Checker

按 inactivityCheckPeriodSeconds 扫描所有设备，超过 inactivityTimeoutSeconds 未上报的标记离线。可关闭。

守护线程

Watchers Thread

周期性检查连接器配置文件变更、清理无效连接器、处理远程配置更新。是 Gateway 的「管家」线程。

可选

Statistics Service Thread

按 statsSendPeriodInSeconds 收集并上报网关自身运行指标。包括系统 CPU/内存、各 connector 的收发字节和消息计数。

可选

ReportStrategy Timer Thread

当存在 ON_REPORT_PERIOD 策略时启动。定时遍历缓存数据点，到期的批量推入 converted_data_queue。

后台

MQTT Client Thread

TBClient 继承 Thread，内部运行 paho-mqtt 的 network loop。处理 MQTT 协议层的收发和心跳。

后台

Async Device Actions Thread

处理设备的异步上下线事件：add_device_async() / del_device_async()，避免 Connector 线程阻塞在设备注册上。

对你项目的启发：线程间通过 SimpleQueue / Queue 解耦，没有共享可变状态。生产者只管 put，消费者只管 get。这个模式你在边缘控制节点的「聚合数据上下文」和「命令编排执行」之间也应该用——用队列隔离采集速率和处理速率的差异。
Modules

模块内部结构

每个模块的源码目录、核心类、关键方法和设计决策。

Connector 层

connectors/ · 18 种协议目录
抽象接口 (connector.py)
open() / close()启动/停止协议连接。每个 Connector 管理自己的生命周期。
is_connected()健康探测。Gateway Service 用它判断是否需要重连。
on_attributes_update()下行通道：平台属性变更推到设备。
server_side_rpc_handler()下行通道：平台 RPC 指令推到设备。
具体实现模式 (以 Modbus 为例)
asyncio 事件循环Modbus connector 在独立线程中跑 asyncio.run()，用 pymodbus 3.9 异步客户端。
Slave 抽象slave.py 封装单个 Modbus 从站的寄存器映射和轮询配置。
Server 模式server.py 可以让 Gateway 充当 Modbus 从站，被外部主站轮询。

Converter 层

connectors/converter.py · 每种协议一对 Uplink/Downlink
核心数据结构
ConvertedData标准输出。__slots__ 优化内存：deviceName, deviceType, telemetry[], attributes, metadata, ts_index。
TelemetryEntry一个时间点的数据。ts（毫秒时间戳）+ values: Dict[DatapointKey, Any]。
DatapointKey不只是 key 字符串——还绑定了 ReportStrategyConfig，实现按数据点的上报策略。
设计决策
ts_index 快速合并ConvertedData 内部维护 ts→index 字典，同一时间戳的数据点自动合并，避免重复 TelemetryEntry。
大包拆分convert_to_objects_with_maximal_size() 按字节限制切分，先放 attributes 再逐条塞 telemetry。

ReportStrategy 层

gateway/report_strategy/ · 数据过滤与聚合引擎
五种上报策略
ON_RECEIVED默认。收到即转发，不做任何过滤。适合已经过前端预处理的数据。
ON_CHANGE缓存每个 DatapointKey 的上一个值，只有值变化才转发。适合状态型传感器。
ON_REPORT_PERIOD定时触发，周期内的数据按聚合函数计算后一次发送。适合高频采集场景。
ON_CHANGE_OR_REPORT_PERIOD值变化立即发 + 定时兜底。适合大多数工业传感器——变化了知道，没变化也定时报个平安。
DISABLED不上报。用于调试或临时屏蔽某些数据点。
配置层级（低覆盖高）
全局 → 连接器 → 数据点全局设默认，连接器可覆盖，单个 DatapointKey 可再覆盖。三级配置合并。

EventStorage 层

storage/ · 三种实现，同一接口
接口设计（event_storage.py）
put(event)写入一条事件。JSON 字符串。
get_event_pack()读取一批。读取后数据不删除——等确认。
event_pack_processing_done()确认这批已处理。Storage 此时才能删除。两阶段提交语义。
SQLite 实现亮点
读写分离写库和读库分开的 SQLite 文件。写满后旋转成读库。避免读写锁竞争。
数据库轮转max_db_count 控制最多几个 db 文件。满了删最老的——天然的 TTL 实现。
线程安全写操作在独立 Thread 中，通过回调通知完成。

TBClient 层

gateway/tb_client.py · MQTT 连接管理
连接能力
认证方式Access Token / X.509 证书 / 设备 Provisioning 三选一。
TLS支持 CA 证书、客户端证书、私钥。ssl.CERT_REQUIRED。
代理通过 socks 库支持 HTTP/SOCKS 代理。受限网络环境必备。
运行时行为
自动重连继承 Thread，run() 中循环检测连接状态。断开后自动重连。
Gateway 协议用 TBGatewayMqttClient，一个 MQTT 连接代理多台设备。设备上下线通过 gateway API 管理。

配置与管理层

tb_utility/ · 远程配置、日志、统计、Shell
远程配置 (RemoteConfigurator)
配置版本对比平台下发新配置时，和本地 CONFIG_VERSION 对比，不同才应用。
10 版本备份ALLOWED_BACKUPS_AMOUNT = 10。每次变更前备份当前配置。
队列式处理配置更新入 RECEIVED_UPDATE_QUEUE，串行处理避免并发冲突。
统计服务 (StatisticsService)
全局指标12 个核心指标：receivedBytes, convertedBytes, sentToTB, eventsAdded/Processed, msgs 等。
装饰器埋点@CountMessage / @CollectStorageEventsStatistics 等装饰器自动在关键路径计数。
Configuration

配置地图

tb_gateway.json 中每个配置项的作用和影响范围。理解配置就是理解系统的调参空间。

配置项默认值作用影响模块
maxPayloadSizeBytes8196单条上行消息最大字节数。超过自动拆包。Storage Fill Thread, ConvertedData
minPackSendDelayMS50两次读 storage 之间的最小间隔（ms）。控制上行发送节奏。Send Data Thread
minPackSizeToSend500积攒到多少条才触发发送。和 delay 配合控制批量效率。Send Data Thread
reportStrategy.typeON_RECEIVED全局默认上报策略。每个连接器/数据点可覆盖。ReportStrategyService
reportStrategy.reportPeriod10000ON_REPORT_PERIOD 的上报周期（ms）。ReportStrategyService Timer
storage.typememorymemory / file / sqlite 三选一。决定断电数据是否持久。EventStorage
storage.max_records_count100000内存存储最大记录数。满了丢新数据。MemoryEventStorage
storage.messages_ttl_in_days7SQLite 模式下消息过期天数。到期自动清理。SQLiteEventStorage
qos1MQTT QoS 等级。0=最多一次，1=至少一次。TBClient
checkConnectorsConfigurationInSeconds60检查连接器配置文件变更的轮询间隔。Watchers Thread
checkingDeviceActivity.inactivityTimeoutSeconds300设备超过这个秒数没上报，标记离线。Device Idle Checker
rateLimitsDEFAULT全局遥测消息速率限制。TBClient
deviceFiltering.enablefalse是否启用设备名过滤。DeviceFilter
remoteConfigurationtrue是否接受平台远程配置更新。关掉就只能本地改。RemoteConfigurator
statistics.statsSendPeriodInSeconds60网关自身指标上报周期。StatisticsService
对你项目的启发：配置地图揭示了一件事——Gateway 的几乎所有运行时行为都可以从配置调整，不需要改代码。你的边缘控制节点也应该做到这一点：上报周期、缓冲策略、速率限制、设备过滤规则，全部配置化，然后通过远程配置下发能力在云端统一管理。

源码目录结构

目录 / 文件行数职责
gateway/tb_gateway_service.py~2370主编排器。线程启动、数据管道串接、所有模块的初始化和生命周期管理。Gateway 的「大脑」。
