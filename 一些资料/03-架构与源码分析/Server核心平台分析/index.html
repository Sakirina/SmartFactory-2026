ThingsBoard 核心平台
架构与数据流拆解

四组件那张图，把 Server / Cloud 画在正中间，说一句"绕不开但不展开"。这一页就是把它展开——设备数据怎么进来，怎么被一层层处理，怎么落库，又怎么实时回到屏幕上。

视角是架构工程师的：不只是标清楚每个框叫什么，而是说清楚为什么是这个结构。消息总线为什么横在中间，Actor 为什么一个实体一个，分区为什么按实体哈希——这些判断比框图本身更值得看。

Architecture

一张图看懂分层

自上而下六层：接入、传输、消息总线、核心处理、支撑服务、持久化。每一层只跟相邻层打交道，跨服务通信全部经过中间那条消息总线——这是整套架构最重要的一根脊梁。

点击放大

读这张图，先抓住第三层——消息总线。它把上面的传输、下面的处理彻底隔开：传输层只管把设备数据塞进队列，处理层只管从队列里取。两边互不感知对方在哪台机器、跑了几个实例，也就各自能独立伸缩。

再看第四层的三个并列服务。TB Core 管状态、订阅和对外接口；TB Rule Engine 管规则链处理；EDQS 专门扛复杂查询。它们都是独立的 ServiceType，集群里可以分开部署、分开扩容。下方那条 Actor 体系是核心处理层的骨架，决定了消息在内存里怎么流。

Layer by Layer

六层逐层拆解

每一层的职责、对应源码、以及一句架构师视角的点评——为什么这层要这么切。每张卡片下方都有入口，点进去是这一层的深入解析。

1

接入层 Access

两类来源：一边是现场设备、网关、Edge 实例，走 MQTT / CoAP / HTTP / LwM2M / SNMP；另一边是人和应用，走 REST 和 WebSocket。

ui-ngx (Angular) 前端
点评：设备和人这两类流量，从入口就被区别对待。设备流量讲究高并发、长连接、协议杂；人的流量讲究会话、权限、实时回推。两条路在这里就分岔了。
深入解析 · 接入层
2

传输层 TB_TRANSPORT

五个协议适配器各管一种接入方式。它们做两件事：校验设备凭据（走 Transport API 往返 Core），把遥测和属性序列化后投进规则引擎队列。

transport/mqttcoaphttplwm2msnmp
点评：传输层故意做得很薄——只认证、只翻译、只转发，不碰业务。这样协议再多、设备再涨，扩的也只是这一层，处理逻辑一行都不用动。
深入解析 · 传输层
3

消息总线 In-Memory / Kafka

所有跨服务通信的中转站。单体默认用进程内内存队列，集群换成 Apache Kafka。主题按用途切开：tb_rule_engine、tb_core、tb_transport.api、通知、用量统计、版本控制等十来个。

common/queue（kafka · memory · provider）
点评：这是全局解耦点，也是削峰的缓冲带。设备瞬时洪峰先进队列，处理层按自己的节奏消费，不会被打垮。换 in-memory 还是 Kafka，本质就是单机和集群的分水岭。
深入解析 · 消息总线
4

核心处理层 Core · Rule Engine · EDQS

三个并列服务加一套 Actor 体系。Core 管状态与对外服务，Rule Engine 跑规则链，EDQS 扛实体查询。消息进入处理层后，由 Actor 在内存里逐级派发。

application/actorsrule-enginecommon/edqs
点评：把"状态服务"和"处理服务"拆开是关键一刀。Rule Engine 可以无状态地水平铺开，Core 守住状态这块硬骨头，各自按各自的瓶颈扩容。
深入解析 · 核心处理层
5

支撑服务 Platform Services

不在主链路上、但缺了就转不动的一圈服务：JS Executor 跑规则脚本，Version Control 给配置做 Git 版本化，Housekeeper 清理级联删除和过期数据，Usage Stats 计量，Discovery & Partition 负责服务发现和实体分区。

msa/js-executorvc-executor · Zookeeper
点评：脚本执行被单独拎出去，是为了把不可信代码关进沙箱、也防止它拖垮主进程。分区服务则是集群能不能正确扩展的命门——它决定每个设备归谁管。
深入解析 · 支撑服务
6

持久化层 Persistence

四块存储：PostgreSQL 存实体、关系、仪表盘、规则链这些结构化数据；时序数据走 PostgreSQL / TimescaleDB 或 Cassandra；缓存用 Caffeine 或 Redis；固件等大文件单独走 OTA 存储。

dao/sqldao/sqltsdao/nosql
点评：结构化数据和时序数据分库，是因为它们的读写模式完全不同。前者要事务和关联查询，后者要的是海量追加写和时间范围扫描——硬塞一个库里，迟早两头都不讨好。
深入解析 · 持久化层
Core Services

三类核心服务 + Actor 体系

核心处理层里那三个并列服务，各自盯着不同的瓶颈。下面这套 Actor 体系，是它们在内存里组织消息的统一骨架。

TB Core

TB_CORE

平台的状态中枢与对外门面。设备在不在线、谁订阅了什么、前端连着哪个 socket，都归它管。

  • Device State — 在线 / 离线状态机
  • Subscription Manager — 遥测 / 属性订阅
  • WebSocket Service — 实时推送给前端
  • REST + Telemetry API — 对外入口
  • Transport API — 设备会话校验
  • Device RPC · OTA · Edge · 告警下发

TB Rule Engine

RULE_ENGINE

数据处理的主战场。从队列拉消息，送进设备 Actor，再沿规则链一个节点一个节点往下走。

  • 规则链消费者 — 拉 tb_rule_engine
  • Filter — 条件过滤、分支路由
  • Enrichment — 补充元数据、关联实体
  • Transform — 改写消息、计算字段
  • Action — 存盘、告警、RPC
  • External — 推 Kafka / HTTP / MQTT 外部端点

EDQS

QUERY

实体数据查询服务。把仪表盘那些复杂的实体筛选、聚合查询，从主库卸到内存里跑。

  • 内存实体索引 — 实体 / 关系 / 最新值常驻
  • Entity Data Query — 复杂查询提速
  • 经 Kafka 订阅变更，保持索引最新
  • 大表格、地图聚合不再压 SQL
  • 独立 ServiceType，可单独伸缩
  • 源码 common/edqs · edqs/

Actor 体系 — 一个实体一个邮箱，消息串行处理

AppActor → TenantActor → RuleChainActor → RuleNodeActor · DeviceActor · CalculatedFieldManager → CFEntityActor

系统根是 AppActor，往下按租户隔离派生 TenantActor，再往下才是设备、规则链、计算字段这些具体实体。每个实体独享一个邮箱，消息排队串行处理——这样同一个设备的状态永远只有一个线程在改，不用加锁，也就没有并发竞争。某个 Actor 崩了，监督机制就地把它重启，影响圈死死锁在一个实体上，不会扩散。

Data Flow

端到端数据流

用序列图看两条主链路：一条遥测从设备走到前端仪表盘（上行），一条 RPC 从前端走回设备（下行）。每条横线就是一次跨组件的消息传递。

点击放大

上行（绿蓝线）：设备发布遥测，传输层先做一次会话校验——拿设备凭据去 Core 换回身份，结果会缓存复用，不必每条消息都验。校验过后，遥测被包成 ToRuleEngineMsg 投进 tb_rule_engine 队列。规则引擎按实体哈希拉到对应分区，交给该设备的 Actor，沿规则链做富化、过滤、转换，最后由存储节点写库。同时一条订阅更新发回 Core，Core 通过 WebSocket 把新值秒级推到仪表盘。

下行（橙红线）：前端发一条 RPC，Core 先定位这台设备此刻连在哪个传输节点上，再把命令发到那个节点的定向通知队列，传输层收到后用设备自己的协议下发。如果是 twoway 调用，设备执行结果会顺着原路一跳跳回传，靠同一个请求上下文把响应和请求对上号。

这里藏着一个容易被忽略的细节：下行之所以要先定位传输节点，是因为设备连接是有状态的、固定在某个节点上，而发起 RPC 的 Core 实例未必就是那个节点。这一跳"找人"，正是分布式有状态连接绕不开的代价。

Design Decisions

几个关键的架构取舍

框图回答"是什么"，这一节回答"为什么"。下面这几个判断，串起来基本就是 ThingsBoard 能横向扩展的底层逻辑。

为什么中间非要横一条消息队列？
直连最省事，但传输层和处理层就被焊死了——一端抖动，另一端跟着抖。队列一隔，两端各自伸缩、各自重启，互不拖累；设备洪峰先进缓冲，处理层按自己节奏消费，再大的瞬时压力也不会击穿。代价是多一跳延迟和一套队列要运维，对 IoT 这种突发流量来说，这笔买卖很划算。
为什么用 Actor，而不是传统线程池 + 锁？
设备状态是天然分片的——A 设备和 B 设备的状态互不相干。一个设备一个 Actor、消息串行处理，等于把"锁"换成了"排队"：同一设备永远单线程改状态，并发竞争从根上消失。出错也只困在单个实体里，监督树就地重启，不波及全局。
为什么分区要按实体哈希，而不是轮询？
轮询能均摊负载，却会把同一设备的连续消息打散到不同节点，顺序和状态就乱了。按 tenantId + entityId 一致性哈希，保证同一实体的消息永远落到同一节点——既守住了顺序和状态一致，又能靠加节点线性扩容。这是有状态流处理的标准解法。
为什么要单独搞一个 EDQS？
仪表盘上那种"筛出某租户所有在线温度传感器并按楼层聚合"的查询，落到 SQL 上又重又慢，还会和写入抢资源。EDQS 把实体和最新值常驻内存、单独成服务，这类查询不再碰主库，主库就能安心扛写入。读写两条路彻底分开，各自扩各自的。
Deployment

单体与微服务，同一套代码两种活法

同样的模块，靠 TB_QUEUE_TYPE 一个开关，就能在"一个 JVM 全装下"和"拆成一片集群"之间切换。这是 ThingsBoard 架构最实用的一处弹性。

维度 单体 Monolith 微服务 Microservices
消息总线 进程内 In-Memory 队列（默认） Apache Kafka，跨节点分区
服务编排 Core / Rule Engine / Transport 同进程 tb-node、各传输、js-executor、vc-executor、edqs 分开部署
服务发现 无需，单实例 Zookeeper 协调 + 一致性哈希分区
缓存 Caffeine 本地缓存 Redis 分布式缓存
适用场景 POC、中小规模、边缘现场 海量设备、高吞吐、需要独立扩容
代价 扩展上限受单机约束 运维复杂度、组件数量显著上升
!

架构师视角：能从单体平滑长到微服务，前提正是前面那条消息总线和按实体分区的设计——业务代码自始至终面对的是"队列"这个抽象，至于队列底下是内存还是 Kafka，它并不关心。架构的弹性，往往就藏在这种"上层无感"的抽象里。
