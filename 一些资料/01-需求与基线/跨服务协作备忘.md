> **用途：** 记录各微服务需求讨论中产生的跨服务依赖、待对齐接口、遗留问题。每个微服务在独立会话中讨论，本文件是会话之间传递"包袱"的唯一通道。  
> **使用方式：**  
> 1. 当某个微服务的需求讨论中发现涉及其他微服务的问题，在此文件中登记一条条目  
> 2. 讨论另一个微服务时，先检查本文件中与该微服务相关的待办项  
> 3. 问题解决后更新状态为 `已解决`，注明解决方式和所在文档位置  
> **格式约定：** 每条条目包含来源、目标、状态、描述、解决建议

### CSC-002 设备注册微服务需定义「设备配置推送」的触发机制与数据格式对齐

| 字段 | 内容 |
|------|------|
| **来源** | 数据传递微服务需求讨论 |
| **目标微服务** | 设备注册微服务 |
| **状态** | `待讨论` |
| **描述** | 数据传递微服务已定义了接收配置推送的接口（方案A: `PushDeviceConfig` gRPC Method; 方案B: `dt/v1/down/{gatewayId}/config` MQTT Topic），包含 `DeviceConfigUpdate` 消息结构（支持设备/Connector 的增删改）。设备注册微服务作为调用方，需确认此接口是否满足其推送需求，或提出调整要求。 |
| **需要设备注册微服务确认的内容** | 1. `DeviceConfigUpdate` 的 `UpdateAction` 枚举是否覆盖所有操作场景（v2.0 新增 `UPDATE_GLOBAL`） 2. `DeviceConfigPayload` 和 `ConnectorConfigPayload` 的字段是否充分（v2.0 新增上报策略配置字段） 3. 批量推送需求（如一次性推送整个 Connector 下所有设备）是否需要额外接口 |

> **⚠️ 跨服务硬需求：`entity_revision`**
>
> `DeviceConfigUpdate` v2.2 新增字段 `entity_revision: int64`（字段编号 5）。**设备注册微服务必须为每个实体（device / connector）维护独立的单调递增版本号**，每次配置变更 +1，填入此字段后再推送。
>
> **为什么：** 数据传递微服务依据 `entity_revision` 判断推送是否过时。仅靠内部到达顺序编号无法区分"新配置"和"旧配置因网络延迟晚到"。没有此字段，乱序保护形同虚设。
>
> **契约：**
> - `entity_revision` 大于本地已应用版本 → 应用变更
> - `entity_revision` 等于本地已应用版本 → `update_id` 去重，忽略
> - `entity_revision` 小于本地已应用版本 → 过时变更，静默忽略
> - 以上三种情况均返回 `success=true`（幂等语义），设备注册微服务无需对 success 做重推判断
>
> **设备注册微服务需求侧纳入点：** 此条应作为设备注册微服务的功能需求之一——"配置推送须携带实体级版本号"。

> **⚠️ 跨服务硬需求 2：字节字段内嵌 JSON 的字段命名契约（P3.5 钉死；已回写接口文档 v2.3 §3.1.2，含 JSON 示例与 strategy_overrides / UPDATE_GLOBAL 语义）**
>
> `DeviceConfigPayload.address / datapoints` 与 `ConnectorConfigPayload.connection / polling / converter` 均为 `bytes`（JSON 编码）。数据传递微服务 P3.5 起将其 JSON 字段名钉死为 **snake_case，与本服务 YAML 配置字段一一对应**（如 `register_type`、`data_type`、`interval_millis`、`unit_id`、`cmd_response_topic`、`report_strategy.period_seconds`）。设备注册微服务生成这些 JSON 时必须使用相同命名；Go 默认字段名（`RegisterType` 等大写驼峰）不再被接受。完整字段清单见 DataTransfer `internal/config/config.go` 的 json 标签。
>
> **补充语义（P3.5 实现落地）：**
> - `DeviceConfigPayload.strategy_overrides`（字段 8）已接通：按 `key` 匹配设备数据点并写入数据点级上报策略；key 不匹配任何数据点时该条 override 被忽略并记 `DT-CFG-003` 警告。
> - `UPDATE_GLOBAL`：`default_report_strategy` 与 `backpressure_policy` 支持热更新即时生效；`queue_capacity` 为启动期参数，运行时推送非零值会被忽略并记 `DT-CFG-003` 警告（如需调整请改本地配置 `runtime.ring_size` 后重启）。
> - `BP_DEGRADE` 背压策略当前自动回退 `BP_BLOCK`（Connector 动态降频能力排期 P4，DT-COL-015）。

| **相关文档** | `数据传递微服务需求分析文档.md` v2.2 FR-S-029a; `数据传递微服务接口文档.md` v2.2 3.1.2 (`DeviceConfigUpdate.entity_revision`), 乱序保护说明; `数据传递微服务软件设计.md` 6.3 |

| 字段 | 内容 |
|------|------|
| **来源** | 数据传递微服务需求讨论 |
| **目标微服务** | 智能命令编排与下发引擎微服务 |
| **状态** | `待讨论` |
| **描述** | 数据传递微服务已定义了下行指令的统一格式：`DeviceMessage` 信封（v2.2 新增 `command_id` 字段）+ `ControlPayload` / `ParamUpdatePayload` / `QueryPayload` 三种 Payload。命令编排引擎作为指令的发起方，需确认此格式能否满足其编排输出的表达需求。 |
| **需要命令编排引擎确认的内容** | 1. `ControlPayload.action` 的字符串标识方式是否足够灵活 2. `CommandOptions`（timeout, retry, priority）是否覆盖了编排引擎需要控制的全部参数 3. 异步指令模式下，回执通过 `CMD_RESPONSE` 上行消息返回，编排引擎是否需要额外的回调机制 4. 指令是否需要支持批量下发（当前接口为单条） 5. P3.5 落地的重试/默认超时语义（见下行“设计决策”第 5 条）是否符合编排引擎预期，尤其 CONTROL 默认 10s 是否过长/过短 |
| **数据传递侧设计决策** | **已写入基线 v2.2：** (1) `command_id` 已提升至 DeviceMessage 信封层（字段编号 6），与 `message_id` 职责分离——`message_id` 追踪消息传输，`command_id` 追踪指令业务生命周期。**命令编排引擎须为每条下行指令分配全局唯一 `command_id` 并填入信封**；(2) FR-S-012 + DT-CMD-005：重复 command_id 被拒绝；(3) 首版单条指令，接口预留批量扩展；(4) `action` 字符串作为索引键，实际协议映射由设备配置中的 action mapping 定义；(5) **P3.5 已实现重试与默认超时**——`CommandOptions.retry_count` 为权威重试次数（0=不重试），仅对传输/执行错误重试（REJECTED 等确定性结果不重试），间隔指数退避（200ms 起、上限 5s）；`CommandOptions.timeout_ms=0` 时按类型取默认超时：CONTROL 10s、PARAM_UPDATE/QUERY 30s。编排引擎若有不同的超时/重试预期，请在对齐时提出。该语义已回写接口文档 v2.3（CommandOptions 注释与 §3.1.3），需求 v2.3 同步修订“默认 3 次”为“调用方指定、0=不重试”（BC-D1 方案一，PM 已裁决） |

### CSC-010 编排体系：共享框架 + 三领域引擎；规则策略编排引擎的定位（概要登记，细节待迭代）

| 字段 | 内容 |
|------|------|
| **来源** | 数据处理中心需求讨论（编排体系分析）；用户对控制引擎概念的纠正 |
| **目标微服务** | 编排与控制中心、数据处理中心、前端可视化系统 |
| **状态** | `待讨论`（架构方向已认可；各引擎节点库与实现待相关迭代） |
| **架构方向（用户已认可）** | 编排体系采用「一套共享编排框架 + 三个独立领域引擎」。共享框架 = 可视化节点编辑器 + 标准对象 + 节点图运行时（前端「编排中心」表现为一个编辑器、三种画布）。三个领域引擎：分析引擎（数据域）、告警引擎（数据域）、规则策略编排引擎（控制域）；边缘侧另有命令编排引擎（执行域）。按数据域 / 控制域 / 执行域分层，越往下风险与权限门槛越高。 |
| **规则策略编排引擎的正确定位（纠正）** | 名称是「规则策略编排引擎」，不是「控制规则引擎」。它编排规则、策略、参数与联动（内容是抽象、概要、上层的：含规则动作、预设方案、多边缘节点联动、反射式联动）；可以借 Kubernetes 声明式的思路来帮助理解，但这仅仅是类比，并不表示它本身就是声明式的。作用对象是**边缘控制节点、不是设备**；通过通知边缘节点去执行某个策略或规则来生效，设备层面的动作由边缘命令编排引擎完成。即便「直接控制」也是通知边缘节点执行预设方案，云端不直接操作设备。 |
| **明确不在本条范围（不涉及实现）** | 各引擎的节点库、标准对象 schema、共享框架运行时实现——均留待相关微服务迭代。 |
