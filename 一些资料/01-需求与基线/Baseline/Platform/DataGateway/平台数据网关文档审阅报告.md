## 一、审核结果

### 1.1 总体判定

两份文档对平台数据网关的定位理解是准确的：把网关当作一个薄而可靠的数据面端点，不做业务建模、不持节点注册表、不解释业务语义，这与需求基线 §1.1 的边界澄清逐条对应。需求覆盖方面，需求基线的 24 条功能需求与 5 条非功能需求中，绝大多数都能在文档中找到明确落点（逐条核对结果见附录 A）；两档确认、下行分流、背压三档、回执配对、插件隔离、凭据分层这些主要设计，与基线的表述一致。

未达准入的原因不在结构与方向，而在几处具体的事实与条款：文档引用边缘已冻结契约时出现了与事实不符的内容（proto 包名、STATUS 消息的语义），有一条平台级需求（有序性）整体没有着落，有一条服务级需求（投递失败处置可配置）的默认行为与基线相反，另有一处接口设计（downlink_id 允许网关代生成）与平台基线条款冲突。这些问题逐条列在第二节，每条都附了依据与具体的修正建议。

### 1.2 做得好的部分（修订时请保留）

## 二、问题清单

严重度分级：**A = 必须修正**（阻碍准入）；**B = 应当修正**（影响契约质量，随本轮修订一并处理）；**C = 基线修正项**（特殊标记——经权衡后修改的是基线而非文档，审阅方已完成，作者按新口径微调）；**D = 细节与格式建议**。

### A 类：必须修正

#### A1 引用的 Protobuf 包名与冻结契约不符

- **位置：** 接口文档 §3（`import "smartfactory/device/v1/device_message.proto"`、`smartfactory.device.v1.DeviceMessage`）。
- **事实：** 边缘已冻结契约的包声明是 `package datatransfer.v1;`（《数据传递微服务接口文档》v2.3 §2.1），不存在 `smartfactory.device.v1` 这个包。
- **问题：** 正文以既成事实的口吻引用了一个不存在的包名。开放项 17.1 虽然写了「proto 的最终落库目录和包名需在 APIContracts 中确认」，但那句话针对的是网关自有的 proto；`DeviceMessage` 是**已经冻结**的契约，把它迁移到新命名空间意味着边缘侧所有 import 路径与生成代码都要变动，属于对冻结契约的破坏性变更，必须作为跨服务变更提案单独提出、由 PM 与边缘侧共同裁决，不能在接口文档里默认它已经发生。
- **修正建议：** 正文引用一律改为 `datatransfer.v1.DeviceMessage`（import 路径相应调整）。如果作者确实想推动统一命名空间，请在开放项里单独写一条「包名迁移提案」，说明动机与影响面，等待裁决；在裁决之前，文档必须以冻结事实为准。

#### A2 「STATUS 心跳 / 状态变更」的分档规则在冻结 schema 上无法执行

- **位置：** 接口文档 §5.2 默认分类表（「STATUS 心跳 → TIMESERIES；STATUS 状态变更 → EVENT」）、软件设计 §3.4（「STATUS 是否按时序档处理由消息子类型和配置决定」）。
- **事实：** 冻结契约中 `MessageType.STATUS` 的注释即「设备状态变更」，`StatusPayload` 只有 `state / reason / last_seen` 三个字段（《数据传递微服务接口文档》v2.3 §2.1、§2.3），没有任何「心跳子类型」字段；整套已冻结的边缘文档里没有出现「心跳」这个概念——设备侧的周期活性并不以 STATUS 消息表达。
- **问题：** 「STATUS 心跳」这一行描述的是一种在现有契约下无法识别、甚至可能根本不存在的流量；设计 §3.4 所说的「消息子类型」在 schema 中没有着落。照现在的写法，实现阶段的工程师拿到一条 STATUS 消息，没有任何字段可以用来判断它该进时序档还是非时序档。
- **修正建议（两个方向，请作者选定其一并写成 DQ 决策记录）：**
  - **方向一（与两侧文本最贴合）：** STATUS 一律按非时序档处理。需求基线 FR-GW-115 本来就把「状态变更等事件」列在非时序；基线里作为时序例子的「设备心跳」，在云边链路上对应的是传输层的 Heartbeat 帧（接口文档 §4.1 已定义），它不进入 `DeviceMessage` 管线。文档写明「设备状态变更走非时序档；连接活性由传输层 Heartbeat 承担，与 DeviceMessage 无关」，分类问题即告消失。
  - **方向二：** 如果作者预期边缘将来会以周期性 STATUS 消息表达设备活性，那么须与边缘侧先行对齐判别方式（例如约定某个 `metadata` 键），在对齐完成之前，分类表中不应出现「心跳」行。
- **附带一处收紧（与本条同源）：** 分类表中 TELEMETRY、EVENT、CMD_RESPONSE 的映射与冻结枚举一致，可以保留。

#### A3 `downlink_id` 允许「由网关生成」与 FR-OC-002 冲突

- **位置：** 接口文档 §6.2 字段规则表（「必填或由网关生成」）、§3 `DownlinkRequest`。
- **依据：** 平台基线 FR-OC-002——「云端的下行请求**自带**请求级标识（用于与边缘回执对应）」。标识由发起方随请求带来，网关不代为生成。
- **问题：** 允许网关代生成之后，发起方要先从 `DownlinkAccept` 响应里取回一个网关生成的 id，再在自己这边登记映射，才能等待回执——「回执复用同一 id」在发起方视角就不闭环了，实际上多出了一套 id 对账。这正是基线想避免的事。
- **修正建议：** `downlink_id` 改为发起方必填生成，删除「或由网关生成」分支；错误码表相应补「`downlink_id` 缺失则拒绝」（可并入 GW-DL-001 或新增编号）。`source_request_id` 作为发起方内部标识可以保留，但请在字段说明里写清它与 `downlink_id` 的分工，避免再添一层歧义。

#### A4 「有序」语义整体缺失

- **位置：** 两份文档均无相关章节。
- **依据：** 平台基线 FR-GW-011 要求边缘通道具备「**有序**、背压、断连续传的云端对端、以及传输层加密（mTLS）」四项能力。后三项在文档中都有明确落点，唯独顺序保证只字未提。
- **问题：** 顺序不是可以默认的事情。举一个具体例子：同一台设备先后上报 `STATUS(OFFLINE)` 与 `STATUS(ONLINE)`，如果网关向数据处理中心的转发不保序，消费方就会得出「设备当前离线」的错误结论。重传与去重对到达顺序的影响、多实例部署（设计 §14.3）下的顺序边界，也都属于必须写明「保什么、不保什么」的内容。下行方向，设计 §6.6「按队列顺序投递」实际上已经隐含了每节点 FIFO，但同样需要明说。
- **修正建议：** 接口文档与设计文档各补一节顺序语义，至少回答四个问题：① 单节点单连接内，上行转发是否保持接收顺序；② 重复消息返回既有 ACK 时，是否影响后续消息的顺序；③ 下行每节点队列的 FIFO 保证（配置类），以及控制类与配置类之间是否存在超越关系；④ 断连重连、多实例接管时的顺序边界。「跨会话不承诺顺序，消费方以消息 `timestamp` 为准」这样的答案也是明确答案——关键是把承诺写出来。

#### A5 FR-GW-117「投递失败处置可配置」未落实，且设计默认行为与基线默认相反

- **位置：** 软件设计 §5.5/§5.6（非时序数据对下游「持续重试直至成功或人工介入」）、接口文档 §13.3 必备配置项表（没有对应配置键）。
- **依据：** 需求基线 FR-GW-117——「投递失败的处置须暴露为可配置项（见 NFR-GW-03），由客户按实际需求选择。**默认：超时即停投 + 触发告警**。」
- **问题：** 基线的默认行为是「重试超过阈值后停止投递、触发告警、等待人工处理」，设计写成了无限期持续重试；同时「处置动作」本身没有出现在配置项清单里，客户无从按需选择。数据不会因此丢失（Journal 仍持久保留，FR-GW-118 的底线没有破），但行为与基线写明的默认值相反。
- **修正建议：** ① 接口 §13.3 增加配置键，例如 `gateway.upstream.event_delivery_failure_action`（取值 `stop_and_alert` / `retry_forever`，默认 `stop_and_alert`）与 `gateway.upstream.event_delivery_timeout_ms`（停投判定阈值）；② 设计 §5.5/§5.6 改写为「按该配置执行，默认超时停投并告警；数据持久保留、不确认丢弃，恢复投递由人工或自动信号触发」。

### B 类：应当修正

#### B1 补盖保留键前缀，两文档不一致

接口 §5.4 规定保留键统一用 `gateway.` 前缀（并明令边缘不得主动写入），设计 §5.3 的表格却使用 `ingress.edge_node_id` 等 `ingress.` 前缀键名，正文还留着「统一使用 `gateway.` 或 `ingress.` 前缀」的两可表述。接口文档是对外契约的权威，请把设计 §5.3 统一改为 `gateway.*`，删去两可表述。

#### B2 回执状态字段命名，两文档不一致

设计 §7.2 称之为 `decision`（通过 / 拒绝 / 执行失败 / 超时），接口 §3 定义的是 `receipt_status`（`SUCCESS / FAILURE / REJECTED / TIMEOUT`）。语义相同、名称不同，请统一为接口文档的 `receipt_status`。

#### B3 `DownlinkPayloadType` 中 CONFIG、MAPPING 两个取值缺少需求出处

需求基线 FR-GW-120/121 列举的下行内容是规则、策略、配置与直接控制。「MAPPING（映射更新）」下发到边缘，在基线中找不到对应需求——模型映射（FR-GW-145）属于外部接入面，在云端执行，不涉及边缘。CONFIG 也需要说明与平台基线 FR-CFG-007 第②层的关系（边缘节点配置由编排与控制中心治理，治理手段是下发规则与策略）。请为这两个取值补出处，或者删除，或者明确标注「预留、本期不启用」。

#### B4 配置键命名，同一文档内不一致

接口 §13.1 示例用 `gateway.downlink.control.default_timeout_ms`，§13.3 表格用 `gateway.downlink.control_default_timeout_ms`（分隔符一个是点、一个是下划线）。请统一，并顺带检查全表的命名规律。

#### B5 配置订阅接口的归属需要注明

接口 §13.2 定义了 `GatewayConfigService.WatchConfig`。按平台基线 FR-CFG-001/002，配置的订阅与热更新协议应当由配置中心统一定义、各服务内嵌客户端，而不是每个服务各自定义一套。这份草案可以保留，但请标注「网关侧期望，最终以配置中心契约为准」，并列入开放项。此事已代为登记到跨服务协作备忘（CSC-014）。

#### B6 凭据接口与「配置中心统一呈现」的衔接未写明

需求基线 FR-GW-144 与平台基线 FR-CFG-005 要求凭据条目纳入配置中心统一呈现、值存加密密钥库。接口 §11 定义了网关侧的凭据管理接口，但没有说明：凭据条目如何出现在配置中心页面上、这些接口由谁调用（配置中心 UI？运维后台？）、权限校验经过权限与身份微服务的路径是什么。请补一段集成说明。此事并入 CSC-014 一并对齐。

#### B7 HTTP 回调形态缺少登记机制

接口 §8.2 写「若发起方登记回调地址，网关按状态变化推送」，但全文没有回调地址的登记接口或配置方式。请补登记方式；或者本期只保留 gRPC `WatchDeliveryStatus` 订阅，把 HTTP 回调标注为预留形态。

#### B8 CMD_RESPONSE 的 `command_id` 校验弱于冻结契约

冻结信封对 `command_id` 的注释是「上行 CMD_RESPONSE 回填对应指令 ID」——必填语义。接口 §5.2 写的是「若存在设备级指令回执，应携带 `command_id`」，比冻结契约松。建议收紧为必填校验：CMD_RESPONSE 缺 `command_id` 按契约错误拒绝，并补对应错误码。

#### B9 FR-GW-116a 的设计裁决没有留下记录

需求基线 FR-GW-116a 允许「事件档若实现代价过大，降级统一按时序处理，触发与否由设计阶段判断」。设计实际选择了完整实现两档、不降级——这正是基线交给设计阶段的判断，结论本身没有问题，但请补一条决策记录（例如 DQ-GW-007：不触发降级，附理由），让这个预留项有可追溯的闭环。

#### B10 上行批量能力未提及

冻结契约定义了 `DeviceMessageBatch`（《数据传递微服务接口文档》v2.3 §2.4，「用于批量上报场景，将多条消息打包发送」），边缘聚合之后的上行流量很可能以批为单位。接口的 `UpstreamEnvelope` 目前只包裹单条 `DeviceMessage`。请评估是否需要批量形态的上行信封（或者说明由 gRPC 流式传输的帧化特性覆盖、批量问题在 CSC-008 对齐时一并确定），并把结论写进文档。

### C 类：基线修正项（特殊标记）

> 这两条的处理方式与其他条目不同：经过权衡，修改基线比修改文档更划算，基线已由审阅方修正完毕。这是渐进明细在基线管理上的正常表现——设计阶段的深入暴露了需求表述的缺陷，经审核与权衡后回写基线。修改前后的原文见第四节 4.1。

#### C1 【基线修正】FR-GW-123 措辞歧义——基线已修正，文档只需微调引用

- **原基线措辞的问题：** 「回执复用**下发指令**的同一 id（**不另设请求标识**）」有两处容易读反。其一，「指令」一词与边缘的指令级 `command_id` 直接冲突，容易被读成「回执复用 command_id」——这恰恰是 CSC-007 明令禁止混用的两个概念；其二，「不另设请求标识」的本义是「不为**回执**另设新标识」，却可能被读成「不设请求级标识」，与 FR-OC-002「下行请求自带请求级标识」表面矛盾。
- **权衡过程：** 作者需要用一整条 DQ-GW-001 专门澄清才绕开了误读，而澄清之后的理解与平台基线 FR-OC-002、CSC-007 完全一致——这说明错的不是设计，而是基线那句话本身。修改一句基线措辞，一次性消除后续所有读者的误读可能；不改基线，则每一份下游文档都得自带一段澄清。前者的性价比明显更高。
- **基线新措辞（已生效）：** 「回执复用其对应下行请求的同一请求级标识，不为回执另设新的标识……该请求级标识与边缘侧的指令级 `command_id` 不得混用（对齐 CSC-007；设计阶段将其命名为 `downlink_id`，见《平台数据网关软件设计》DQ-GW-001）。」
- **对文档的要求：** DQ-GW-001 保留；其中引用基线原文「回执复用下发指令的同一 id」的地方，请更新为基线新措辞。

#### C2 【基线修正】FR-GW-110 补「资产管理不可用」的缺省行为；fail-open 是否提供，交 PM 裁决

- **背景：** 基线原文只规定「未在册或处于停用的节点，不得接入」，没有回答「准入核验所依赖的资产管理服务不可用时怎么办」——这是基线的一处空白。两份文档给出的方案是「默认 fail-closed（拒绝接入）；是否允许短时 fail-open 作为高风险配置项并写审计」（设计 §4.2、接口 §4.3 UNKNOWN 行、§15.1 GW-AUTH-004）。
- **权衡过程：** 「默认拒绝」与基线「未在册不得接入」的精神一致，属于把空白补实，值得固化为需求条款；而「是否提供 fail-open 配置」是安全性与可用性之间的取舍——一边是资产管理故障期间边缘节点全部无法接入的可用性风险，一边是核验缺位期间不可信节点混入的安全风险——这个决定涉及安全边界，信息不足，不是文档审阅可以代替 PM 做的。因此基线只固化「默认 fail-closed」，fail-open 列为需求层面待决项，由 PM 裁决。
- **对文档的要求：** 涉及 fail-open 的三处表述（接口 §4.3 admission_status 表 UNKNOWN 行、§15.1 GW-AUTH-004、设计 §4.2 末条）请统一改为「默认拒绝；fail-open 配置是否提供，待 PM 裁决，裁决前不实现」的口径——现在「除非高风险配置允许短时 fail-open」的写法，读起来像这个配置已经存在。

### D 类：细节与格式建议

- **D1** 接口 §8.4 的表格分隔行缺行首竖线（`----------|` 应为 `|----------|`），部分渲染器下表格会断裂。
- **D2** 接口 §16 验收对齐表与设计 §17 需求覆盖矩阵目前用描述性短语指代需求，建议改用 FR-GW-xxx / NFR-GW-xx 编号，并补 NFR 各条的行——编号化之后，逐条核对不再需要人工比对语句，追溯成本低得多（本报告附录 A 可直接取用）。
- **D3** 设计 §1.3「不纳入范围」表建议补一行「预约执行调度 —— 归边缘（云端不持有预约调度，FR-GW-121）」，这是基线特意写明的边界，值得在设计里同样显式。
- **D4** `RELIABILITY_CLASS_EVENT` 与 `MessageType.EVENT` 同名容易混淆——§5.2 的表里会出现「EVENT 类型对应 EVENT 档」这样的行。趁契约未冻结，建议将可靠性档位更名，例如 `RELIABILITY_CLASS_NON_TIMESERIES`。
