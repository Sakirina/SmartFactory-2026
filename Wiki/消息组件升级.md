# 消息组件升级与冷备恢复

[Wiki 首页](README.md) · [备份与恢复](operations/backup-restore.md)

当前正常部署采用 Kafka 4.3.1 和 NATS 2.14.7，NATS 2.12.15 用于从 2.11.9 升级的中间阶段。镜像及来源以[依赖清单](../deploy/dependencies.json)和[内容锁](../deploy/images.lock.json)为依据，升级检查在独立项目记录旧内容、消费位置、执行权及实际挂载。

## 镜像与备份

1. 查看所需镜像，联网准备主机按锁取得目标和中间版：

   ```sh
   python3 scripts/pull-images.py --only kafka nats nats_upgrade_intermediate
   python3 scripts/pull-images.py --execute --only kafka nats nats_upgrade_intermediate
   ```

2. 离线交付通过 docker image save 保存精确引用，另存归档 SHA-256，目标主机加载后核对实际版本、架构、摘要和 Compose 引用。
3. 停止对应服务，保存完整数据、配置、凭据与证书，核对冷备文件摘要、消息状态及实际挂载源。
4. 在独立恢复目标检查备份内容后安排程序及格式升级。

## Kafka：程序和元数据

受测迁移从 4.0.0、KRaft 元数据 4.0-IV3 开始。程序切换与元数据推进各自形成检查阶段，推进前冷备保留旧程序可读取的内容。

1. 停止源 broker，记录主题、各分区末端偏移、消费组位置和 kafka-features describe，复制完整目录并保存逐文件摘要。
2. 用原目录启动 4.3.1，维持 4.0-IV3，检查旧消息、新消息及消费位置。此阶段的隔离验证完成目标停止与 4.0.0 再次启动。
3. 验证完成后停止服务并再次冷备，再启动目标执行元数据推进：

   ```sh
   /opt/kafka/bin/kafka-features.sh \
     --bootstrap-server localhost:9092 \
     upgrade --release-version 4.3
   ```

4. 确认 4.3-IV0 后检查新增消息与重启。恢复旧版采用推进前冷备及新的独立挂载源，先核对宿主机与容器只读挂载内的摘要，再启动源程序。
5. 检查恢复时点之后的消息和消费位置，根据上游资料补回后续记录，再恢复业务。

正式 JVM 最大堆为 512 MiB、容器上限 1 GiB，broker 就绪探针独立使用 96 MiB 最大堆和协议请求。隔离检查脚本要求已缓存脚本声明的源、目标和存储初始化镜像，创建新的私有目录并记录命令、挂载与冷备：

```sh
python3 scripts/check-kafka-upgrade.py \
  --directory /tmp/sf-kafka-upgrade-review
```

## NATS：逐节点升级

受测路径为 2.11.9 → 2.12.15 → 2.14.7，三个服务器保留各自身份、JetStream 目录、客户端和路由 mTLS。每阶段读取当前 metadata leader，处理 follower 后再处理 leader。

1. 在源版保存 R3 文件型 KV 执行权和签名检查点，核对三节点读取、复制及证书，全部停止后冷备并检查源版再次启动。
2. 对当前 follower 发送 SIGUSR2 进入 lame-duck，等待退出，用相同目录和下一阶段镜像启动。
3. 核对实际版本、成员、路由、metadata 与 KV 副本 current 状态，确认完成后处理下一个节点，最后处理该阶段 leader。
4. 三节点全部进入 2.12.15 后执行同样过程进入 2.14.7。
5. 在目标取得新执行权，核对旧 owner 与旧检查点写入拒绝、单节点和全节点重启以及法定多数故障处理。

正常生成器每节点设置 256 MiB 内存、192 MiB Go 软上限和 2 GiB 文件存储逻辑上限。迁移夹具为多个验证命名空间设置独立预算，并记录实际文件占用，资源判断读取对应场景报告。

## 独立 NATS 夹具前提

prepare-site.py 生成独立配置和 TLS 材料，使用 `--root` 指定含镜像锁的根目录、`--project` 指定项目、`--binary-dir` 指定当前主机 PKI 程序目录。以下仅准备配置：

```sh
SF_FIXTURE='/tmp/sf-message-review'
mkdir -p "$SF_FIXTURE/deploy"
cp deploy/images.lock.json "$SF_FIXTURE/deploy/images.lock.json"
python3 scripts/prepare-site.py \
  --root "$SF_FIXTURE" \
  --project sf-message-review \
  --binary-dir "$PWD/bin"
```

| check-nats-upgrade 所需条件 | 准备内容 |
| --- | --- |
| 独立项目 | Compose name 以 sf-message- 开始，每个服务的 sf.evolution.fixture 标签等于项目名 |
| 数据目录 | 各 /data 指向该项目自己的 data-nats-1、data-nats-2、data-nats-3 bind 目录 |
| 源镜像 | 使用脚本及源记录对应的 2.11.9 摘要，目标和中间镜像已缓存 |
| 退出参数 | lame_duck_grace_period 为 1s，lame_duck_duration 为 30s |
| 端口 | 客户端 14222 至 14224，监控 18222 至 18224，未被其他实例使用 |
| 协调程序 | 本次源码的 coordination.test 位于夹具根目录，TLS 与 SQLite 材料由对应夹具使用 |

完成这些前提后，在源码根目录构建协调测试并执行检查；中间引用由锁定文件读取：

```sh
go -C Platform test -c -o "$SF_FIXTURE/coordination.test" ./internal/coordination
SF_INTERMEDIATE=$(python3 -c 'import json; print(json.load(open("deploy/images.lock.json"))["images"]["nats_upgrade_intermediate"]["pinned"])')
python3 scripts/check-nats-upgrade.py \
  --directory "$SF_FIXTURE" \
  --intermediate-image "$SF_INTERMEDIATE"
```

该脚本修改和删除自己标记的夹具服务，保存复制、检查点及协调结果。检查内容与正式持久部署区分记录，三节点连续断云及长时间容量采用[目标环境专项](releases/1.1.md)。

## 冷备恢复

NATS 恢复采用三个配套目录、原服务器名称、配置、路由凭据、CA、节点证书及签名密钥，保存恢复后的服务器 ID。停止全部目标服务后复制到独立目录，核对消息条数和首末序号、流配置、执行权及签名检查点，再核对备份之后的命令与物理效果。

既有隔离迁移结果包含 source-cold-backup 和配套身份时，可用恢复检查器；source 指向完整迁移夹具，directory 为新目录，所需端口和原镜像事先准备：

```sh
python3 scripts/verify-nats-cold-restore.py \
  --source /tmp/sf-message-review \
  --directory /tmp/sf-message-cold-restore-review
```

恢复检查取得新的执行权并核对旧 owner 写入拒绝，加入原执行域前处理备份之后的步骤与消息。业务库和 PostgreSQL 主版本卷按[备份恢复](operations/backup-restore.md)配套处理。
