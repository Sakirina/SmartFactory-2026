# 组织、权限与审计

[Wiki 首页](../README.md) · [控制执行](control.md)

人员身份、角色、资源范围和团队授权共同决定业务许可，部门关系参与领导会签资格。管理员在云端维护正式授权，现场使用签名权限包取得对应节点的人员与资源资料。

## 角色和资源

| 角色 | 基础能力 |
| --- | --- |
| `admin` | 管理人员、配置、插件和审计，并执行授权业务 |
| `engineer` | 查询、设备登记、定义编辑与发布、大屏维护和工程师会签 |
| `leader` | 查询及组织范围内的领导会签 |
| `safety` | 查询及指定现场安全确认 |
| `viewer` | 读取授权资源 |
| `ai` | 查询与定义草稿编辑 |

角色对应操作类型，资源对应对象；工厂或车间资产的授权沿层级覆盖下属对象，团队授权还指定规则组、动作与资源。服务逐项核对请求引用的设备、定义及依赖，当前对象状态也参与操作判断。

## 维护流程

1. 管理员进入“组织与权限”，阅读人员、部门、团队和启用状态。
2. 使用“管理授权”调整角色、资源和团队，或通过“配置团队授权”维护规则组及动作。
3. 组织关系更新通过“导入组织变更”或[同步插件](../development/extensions.md)提交，核对来源和递增序号。
4. 用受影响账号检查当前可见资源及操作条件，再核对审批资格和现场同步状态。

组织同步保存来源与序号，同一同步身份重交时检查内容一致性。人员停用、组织移动与资源变化影响后续许可，历史审计保存当时身份和判断资料；页面在会话或权限变化后清除受影响缓存。

## 初始账号和二次认证

示例初始化提供 `admin`、`engineer`、`engineer2`、`leader`、`safety`、`viewer` 和 `assistant`，使用部署生成的初始密码。实际人员通过用户 API 或组织同步建立，再配置各自密码、角色、资源与认证资料。

用户 API 使用 `totp_secret` 设置二次认证，实际安全员采用组织分发的独立密钥。现场登录时提交当前验证码，服务保存有时限的认证状态；安全确认还核对预案指定人员、目标节点、本地会话和会签条件。

## 离线授权与审计

边缘权限包保存节点、授权版本、到期时间及签名，默认有效 48 小时，联网时持续更新。暂时断云期间，现场按已同步资料查询本地数据和执行正式预案；到期或签名校验失败后，恢复授权同步才能继续相应操作。参数见 `identity.offline_ttl_ms`，该有效期与[节点程序配置缓存](node-releases.md)采用各自机制。

管理员在“业务审计”按请求查询，阅读来源序号、人员、资源、版本及条件，再执行完整性校验。服务检查哈希链和签名检查点，出现问题时保存原记录并核对来源及配套备份；执行详情可按相同身份阅读审批、命令与回执。
