# 审批与控制执行

[Wiki 首页](../README.md) · [工单与交接](business-workbench.md)

人工控制固定已发布预案、参数和风险依据，符合条件的人员完成会签后正式下发，设备步骤在所属现场执行。执行详情保存审批、条件、原命令证据、人工请求与反馈时间线，供人员判断本次设备操作的实际状态。

## 会签与启动条件

| 请求类别 | 默认条件 |
| --- | --- |
| 普通即时控制 | 一名工程师及一名符合发起人组织关系的领导 |
| 业务强制执行 | 两名工程师及一名符合组织关系的领导 |
| 安全强制执行 | 强制执行会签，再由预案指定安全员在目标现场完成二次认证确认 |

每名人员在本次请求承担一个会签角色，并具备当前角色与资源许可。默认会签及二次认证窗口均为五分钟，正式下发后十秒内开始执行；这些条件由[配置中心](../reference/configuration.md)管理。物理联锁在审批和设备步骤前检查，联锁生效时阻止对应动作。

## 发起和正式下发

1. 在“审批与执行”发起即时控制，选择正式预案、填写参数和请求理由，核对强制选项、风险类别及现场条件。
2. 打开详情，阅读预案版本、判断时观测和所需确认；各审批人员用自己的账号完成对应角色确认。
3. 会签满足后，由具有控制许可的人员正式下发，服务重新检查人员授权、审批有效期、预案与风险依据。
4. 查看设备步骤、命令回执和反馈时间线，再在数据监控中核对相同设备的实际反馈字段。

安全确认使用目标节点的本地会话，登录现场页面时提交当前二次认证码。参数、正式预案或判断依据改变后，按当前条件建立新的审批请求；人员停用、授权变化及审批过期会改变可下发状态。

## 状态与人工处理

| 状态 | 对应行为 |
| --- | --- |
| `awaiting_approval` | 等待所需人员确认 |
| `approved` | 审批满足，等待正式下发 |
| `queued`、`running` | 等待现场或正在执行设备步骤 |
| `completed`、`degraded_completed` | 正常或按降级步骤完成 |
| `result_unknown` | 原命令发送后等待确定证据 |
| `failed`、`rejected` | 读取失败条件、判断依据与当前允许操作 |

自动策略与调度也建立执行实例，采用预案条件、风险和现场联锁；其记录与人工即时控制共同显示在执行页面。

1. 结果未知时核对原请求、预案、云端业务版本和边缘来源版本，阅读 `allowed_actions`。
2. 填写人工理由并提交“核对原命令结果”，使用同一操作身份追踪受理、开始和终止回执；云端离线受理可能返回 HTTP 202。
3. 阅读原命令设备、内容摘要、反馈来源、可信状态和观测／采集时间，再结合现场状态判断结果。
4. 服务允许后提交“恢复剩余步骤”，核对已经完成动作和后续步骤；取消停止后续执行，已发送命令及迟到反馈保留关联记录。
5. 版本冲突时读取最新状态并保留理由，核对新条件后再次提交。

## 命令身份与多节点执行

外部请求使用 `downlink_id`，各步骤使用由执行与步骤确定的 `command_id`，DataTransfer 在发送前保存动作日志。相同请求和内容重交取得已保存状态，同一身份改变内容返回冲突；结果未知时继续核对原命令及原执行。

多节点预案通过 NATS JetStream 保存执行权和签名检查点，各节点核对固定定义版本与摘要。多数节点或参与节点通信条件失效时，按预案配置采用本地降级步骤；恢复后对照原命令、检查点和实际设备效果继续核对。
