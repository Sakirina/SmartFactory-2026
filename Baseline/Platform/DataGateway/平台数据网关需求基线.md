## 1. 概述

### 1.1 定位

平台数据网关是云端平台与边缘控制节点之间的**唯一对边出口**，同时承担外部系统的接入。它把边缘上行的数据可靠地接进平台、把云端的下行可靠地送达边缘，并为人事/MES/ERP 等外部系统提供插件式接入。

**纳入范围：**
- 边缘上行数据（设备数据、操作事件、执行反馈）的接入、校验、去重、路由；
- 云端下行（规则、策略、直接控制）的可靠送达，以及边缘回执的配对回传；
- 外部系统的插件式接入与组织数据导入；
- 连接入口的可信校验（mTLS 终结 + 节点准入核验）。

**边界澄清（网关不承担）：**
- 不做业务建模与上层概要抽象——沿用边缘已产出的 `DeviceMessage`，资产/分析的抽象交给数据处理中心；
- 不持有边缘节点注册表——节点身份与准入状态归资产管理（网关只在门口核验）；
- 不治理边缘节点配置与设备配置——前者归编排与控制中心，后者归边缘命令编排引擎；
- 不充当业务规则引擎或安全联锁执行者。

### 1.2 核心职责

平台数据网关的本分，是把「传递数据」这件事做到可靠：**接入、校验、去重、可靠投递、路由、对外接入**。它是一个可靠的数据面端点，分量轻、无业务逻辑。

### 1.3 在云边架构中的位置

- **上行：** 设备 → 数据传递微服务 → 边缘聚合 → 边缘↔云传输模块 →（mTLS）→ **平台数据网关** → 数据处理中心；
- **下行：** 编排与控制中心 → **平台数据网关** →（mTLS）→ 边缘↔云传输模块 → 边缘命令编排引擎 → 数据传递微服务 → 设备；
- **回执：** 边缘 → 边缘↔云传输模块 → **平台数据网关** →（按请求标识配对）→ 编排与控制中心；同时进审计。

### 1.4 设计原则

1. **单租户。** 无多工厂共用一套的情形，数据模型不带租户维度。
2. **谁接收谁负责。** 每一跳由接收方去重、发送方负责可靠投递（投到没有、要不要重投）；边缘与云端两侧对称配备发送缓冲与接收去重。
3. **两档可靠性。** 时序数据（传感、心跳）收到即确认、可容损；非时序数据（事件、回执、配置、规则策略）存妥才确认、丢不得。
4. **下行按紧迫度分流。** 配置类下行可缓冲重投、最终送达；控制类下行有时限，节点不可达或超时则快速失败、回报状态。
5. **凡「看情况而定」皆可配置。** 超时、重试、频率、策略等暴露为配置项，接入配置中心。
6. **薄而可靠。** 网关无业务逻辑，只把数据面做扎实。

## 2. 部署与租户形态

**FR-GW-101** 平台为单租户：不支持多工厂共用一套实例，数据模型不引入租户维度。

**FR-GW-102** 平台须支持两种托管形态：**代理云端托管**（厂商为每个客户各起一套彼此独立的实例）与**协助自托管**（客户自持基座与信创环境，厂商提供协助）。两种形态下网关职责一致。

## 3. 功能需求

### 3.1 边缘通道面 · 上行接入

#### 3.1.1 连接与信任

**FR-GW-110** 网关须终结边缘节点的 mTLS 连接，并以连上来的节点身份，向资产管理核验其准入状态（启用/停用）；未在册或处于停用的节点，不得接入。

**FR-GW-111** 网关不持有节点注册表；「哪些节点可信」的事实来源是资产管理，网关仅在连接入口执行核验。

#### 3.1.2 归一化：校验 + 透传

**FR-GW-112** 网关对上行数据做**校验 + 透传**：沿用边缘已冻结的 `DeviceMessage`（Protobuf），不在云端二次建模。资产与上层概要的抽象交由数据处理中心。

**FR-GW-113** 网关可在透传时补盖必要的接入侧标识（如接入节点、接入时刻），不改动 `DeviceMessage` 的既有语义字段。

#### 3.1.3 可靠投递与去重

**FR-GW-114** 上行投递遵循「谁接收谁负责」：作为接收方，网关须对上行消息去重；作为对端，边缘负责重传直至收到确认。

**FR-GW-115** 确认语义按数据性质分两档：
- **时序数据**（传感读数、设备心跳等持续数据）：确认 = 网关已收到（不等下游消费），溢出时丢弃最旧的一段；
- **非时序数据**（状态变更等事件、操作事件、执行反馈等）：确认 = 网关已持久存妥并完成去重，发送方收到确认才停止重传；溢出时继续持久保存、等待人工介入。

**FR-GW-116** 去重以 `message_id` 为键；发送方重传时须复用同一 `message_id` / `command_id`，不得每次新生成。

**FR-GW-116a** 事件档若在实现上代价过大，允许降级统一按时序处理（触发与否由设计阶段判断）。

#### 3.1.4 投递失败处置

**FR-GW-117** 投递失败的处置须暴露为可配置项（见 NFR-GW-03），由客户按实际需求选择。默认：超时即停投 + 触发告警。

**FR-GW-118** 溢出、缓冲满时：时序数据丢弃最旧的一段；非时序数据继续持久保存、等待人工介入。该策略与边缘数据传递微服务一致，并在其上补充「按时序/非时序分别处置」。

### 3.2 边缘通道面 · 下行与回执

#### 3.2.1 下行内容与分流

**FR-GW-120** 下行内容为业务抽象层的规则、策略与直接控制，不含设备级协议帧（翻译由边缘命令编排引擎完成）。

**FR-GW-121** 下行按紧迫度分两类处置：
- **配置类**（规则、策略、配置）：非时序持久档，节点离线时缓冲、重连后续投，保证最终送达。其中「到某个时间点才执行」的预约，由边缘收到规则后在本地按时触发，云端不持有预约调度。
- **控制类**（直接控制）：用于应急处置、产线变更等罕见情形，须有工程师与上级领导在场、即时执行，不存在预约执行；带时限（参照边缘 CONTROL 默认 10 秒），节点不可达或超时则**快速失败**，回报状态给发起方，不缓冲投递已然过时的控制指令。

**FR-GW-122** 网关按目标节点标识路由下行；目标节点离线时，配置类下行进入持久缓冲、待重连。

#### 3.2.2 回执配对与路由

**FR-GW-123** 回执复用下发指令的同一 id（不另设请求标识）。发起方按该 id 等待、匹配回执、并做执行超时处理；网关据同一 id 将回执路由回发起方。

**FR-GW-124** 直接控制的回执（含风险评定、上下文）在回传发起方的同时，须进入审计事件流（高风险操作链证据，对齐 CSC-007）。

#### 3.2.3 云 → 边背压反馈

**FR-GW-127** 下行收发以队列承载。队列须设三档水位阈值——**提醒、警告、错误**；队列大小与各档阈值经配置文件调整，并接入配置中心。

**FR-GW-128** 网关须向发起方如实回传下行的投递状态（在途 / 已达 / 超时未达 / 失败），使发起方掌握下发是否送达。

**FR-GW-129** 当下行队列水位升高，须按提醒 / 警告 / 错误三档向上游（编排与控制中心）回传压力信号并施加背压，使其放缓乃至暂停下发，避免队列被撑满。

**FR-GW-130** 断连期间：配置类下行排队、重连后续投；控制类下行按 FR-GW-121 快速失败回报。

### 3.3 外部接入面

**FR-GW-140** 网关须提供自定义插件接口与开发套件（SDK）。

**FR-GW-141** 第三方接入插件须进程级隔离运行，独立于网关主进程；插件崩溃或越权不得波及主链路与边缘通道面。

**FR-GW-142** 本期插件方向为只接入（外部 → 平台）；SDK 须预留对外写出的方向位，留待后续按需启用。预置的人事插件只导入企业组织（架构、下属成员、职员等级），不向外送数据。

**FR-GW-143** 外部同步形态：以外部系统主动推送为主、平台定时拉取为兜底；数据处理默认增量、支持全量。

**FR-GW-144** 对外凭据由网关统一管理（统一凭据库）：凭据条目纳入配置中心统一呈现，其**值**须存于加密的密钥库、界面打码显示，不与普通配置同等明文保存。

**FR-GW-145** 模型映射（外部 schema → 平台模型）须在数据治理工具中定义、版本化；字段命名与边缘已冻结契约保持一致（snake_case，CSC-002）。

## 4. 非功能需求

**NFR-GW-01（可靠性与断联自治）** 网关须支持断连恢复与续投；边缘断联期间，配置类下行排队待投，上行接入恢复后续传。

**NFR-GW-02（安全）** 边缘连接 mTLS；对外凭据入密钥库；第三方插件进程级隔离。

**NFR-GW-03（可配置性）** 所有「看实际情况而定」的项（超时、重试频率、超时动作、溢出策略、拉取频率、全量/增量等）须暴露为可配置项，并接入配置中心；变更带版本、受权限管控、写审计。

**NFR-GW-04（信创合规）** 入库、传输加密、密钥库均满足信创与国密要求。

**NFR-GW-05（部署形态）** 须同时适配代理云端托管与协助自托管两种形态。

## 5. 数据与契约对齐

- 沿用边缘已冻结信封：`DeviceMessage`、`command_id`、`message_id`、`entity_revision`（CSC-002）。
- **云↔边可靠投递契约（谁接收谁负责、两档确认、接收方去重）** 是一条牵动边缘↔云传输模块的对称契约，已概要登记为 **CSC-008**（不含实现）。
- 直接控制请求/回执对齐 **CSC-007**。
